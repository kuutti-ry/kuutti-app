# ADR-020: End-to-end flows with Maestro

- Status: accepted, amended 2026-10-11 (§6: Android in CI, on `main` and on a pull request when asked; §7: four jobs, in an order, #226) and 2026-10-19 (§8: a second phone over HTTP, #349)
- Date: 2026-10-10
- Follows: issue #164

## Context

Routes have their `app.request()` tests and the demo stories run through the real routes, but nothing drove a screen: sign-in, onboarding, the field screens and the card were checked by hand, on a simulator, from a chart. Each round of that costs an evening. #164 asked for flows that drive the app against the local environment, starting from the demo cast, and left the driver to the maintainer.

## Decision

1. **Maestro** drives the mobile app: YAML flows under `apps/mobile/e2e/`, one file per behaviour, the same files for iOS and Android, run by `pnpm e2e` (`maestro test apps/mobile/e2e/flows`). Maestro is a tool on the developer's machine (Homebrew, Apache-2.0), not a dependency of the workspace, so `scripts/license-policy.json` is untouched.
2. **The mock bank only**, as #164 says: a flow signs in through the system browser at `services/mock-idp`'s page as a persona named by their name on that page; Telia's bed and staging stay for people.
3. **The dev client build** on a booted simulator, the bundle opened by the dev client's launcher link to Metro, so a flow never sees the launcher screen.
4. **Local first.** CI comes later, on an Android emulator on a Linux runner, which is cheap where a macOS simulator runner is not.
5. **Texts in three languages.** The app speaks what the phone or the person chose, so every tap and assertion names its text in English, Finnish and Swedish as a regular expression; the texts are those of `messages.yaml`, and a flow that matches on a key's text breaks when the text changes, which is the point.
6. **Amendment of 2026-10-11: Android in CI, on `main` and on a pull request when asked.** §4's CI is `.github/workflows/e2e.yml`: the flows on an Android emulator (API 36, x86_64) on a standard `ubuntu-latest` runner, free for a public repository, where the emulator has KVM and `docker compose` runs as on a laptop; macOS runners would give the iOS simulator but have no Docker, and Maestro Cloud or EAS's Maestro step would need the local stack reachable from outside, against §2. The runner starts the stack from `env.example`, the API from source, a dev client built there and Metro, and the emulator's loopback is reversed to the runner (`adb reverse`), so the flows and the app name no other host. The same files run on iOS on a laptop and on Android in CI; where the platforms differ (a switch's state, the browser's first-use screens, the keyboard), a flow says both, and the README says how. Its cost, measured on the first runs of 11/10/2026: about 13 minutes to build the dev client and 1.4 minutes a flow, close to an hour for the 27, more than half of it bringing each flow to its signed-in start. So it runs on every push to `main`, on a pull request that carries the label `e2e` and changes what the flows exercise (each push while the label stays), and by hand (the maintainer, 11/10/2026). The dev client is cached by its Android fingerprint and saved as soon as it is built, so a run builds it only when the native side changed (7 of 96 pushes to `main` from 20/09 to 11/10/2026). The flows' own overhead is #226. Considered: the dev client of `eas-build.yml` fetched by its fingerprint (`eas build:download`), rejected since it needs `EXPO_TOKEN` in a job that runs the pull request's code, the free queue lags a native change, and a pull request that changes the fingerprint builds anyway. A split across jobs is the change to make if every pull request should run the flows.
7. **Amendment of 2026-10-11: four jobs, in an order (#226).** One job ran the flows one after another for close to forty minutes, and setting one up costs about three. The flows now run in four jobs, each a stretch of the order in `config.yaml`'s `executionOrder` on its own emulator and stack, so no two jobs share a persona or a database; one job before them finds the dev client by its fingerprint or builds it, so it is never built four times. A stretch ends where the flows' weight (their commands, a sign-in counted as ten) passes a quarter of the whole, which kept the four within about 10 % of each other on the times of the last single run; the order keeps each persona's flows together, so a stretch reads as a story and a cut seldom splits one. It costs the setting up of three more jobs, about ten runner minutes a run on runners that are free for a public repository, and the wait falls to about a quarter.
8. **Amendment of 2026-10-19: a second phone over HTTP (#349).** Maestro drives one device, and a live chat needs somebody writing from another. The flow's own script is that somebody: Maestro's `runScript` calls the API over HTTP as the other persona while the flow watches the screen (`flows/chat-live.yaml`, `e2e/scripts/ville-*.js`). Its session is made before the run by `scripts/e2e.ts`, which signs the persona in at the mock bank on this computer with the demo commands' own `loginAs`, only when the flow is among those to run, and hands Maestro the refresh token and the API's address; the script trades the token for an access token when it writes. Maestro's HTTP follows redirects, so a script cannot walk the bank login itself. No route exists for the purpose: the persona signs in as anybody does.

## Consequences

- `apps/mobile/e2e/common/sign-in.yaml` and the first feature flow, `flows/language.yaml`; a README for the next flows; `pnpm e2e` in the root and in CLAUDE.md's commands.
- The chart of manual checks of 10/10/2026 (#213, #146, #178) was the backlog; it and the cast's stories are now flows, one persona to each where it changes something, so the order does not matter (`apps/mobile/e2e/README.md` has the table). The workspace is `apps/mobile/e2e` (its `config.yaml` runs `flows/*`), so `common/` and the copy of the pictures `scripts/e2e.ts` makes for `addMedia` lie inside it.
- Left for later, each its own change: the admin panel with Playwright; iOS in CI; a dev-only sign-in link that completes the mock IdP's login for a named persona, if the system browser proves flaky under Maestro (it touches identity: an ADR and the security reviewer); the storyboard's scenes as flows; a `--only <persona>` reset.
