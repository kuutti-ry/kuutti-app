# ADR-018: Staging is the demo environment, and the stories are written inside the API

- Status: proposed (the maintainer's acceptance closes #141)
- Date: 2026-10-08
- Follows: ADR-014 (demo mode: the personas, the population, the histories; §9, §10, §11 and §12 amended here), ADR-010 §10 (one pond), ADR-013 (the counter never recounted in a deployed environment, excepted here for staging), ADR-016, `docs/vendors/telia.md` 1.4 (the test persons of the bed), TD-1, TD-7, TD-19, CLAUDE.md rules 1, 2 and 6, `docs/security-checklist.md`; issue #141 (replaces the staging part of #73)

## Context

Locally the personas get their stories by logging in at the mock bank and sending their answers through the API's own routes (ADR-014 §12), so nothing outside the API ever derives an identity's hash. On staging the bank is Telia's pre-production bed, which no script drives: a persona's story there has to be written another way, or staging shows an empty app. The maintainer decided on 08/10/2026 that staging is where the demo lives: on real strong authentication (Telia's test users, #140), with stories, a population and, with #142, pictures, so that anybody with the staging build can repeat the first ten minutes. That needs a rule about what staging holds and a way to write the stories that keeps rules 1 and 2.

## Decision

1. **Staging holds no real person, ever.** Its identities are the test persons of Telia's bed, whose codes are artificial (an individual number of 900 to 999, which the population register gives nobody, ADR-014 §3), and the synthetic population of ADR-014 §8. A real person does not sign in on staging; a build that reaches a person is production's. The privacy notice says nothing of staging because nobody is there.
2. **The stories are written by a job that runs inside the API's container, and nowhere else.** `node dist/demo-stories.js` (`apps/api/scripts/demo-stories.ts`, built into the image beside `dist/index.js`) does what a registration does, in the one place that holds the key: it reads its configuration as the API reads it, through the instance role from the environment's own parameter store; derives each persona's hash from its artificial code with that key (`deriveArtificialIdentity` in the identity slice, which refuses a code a person could have before deriving anything, so what leaves the slice can never be a person's hash); creates the identity and the account as the callback would (`decideRegistration`, the same rule, so a banned persona or one inside its waiting time is refused by the code that refuses people); and gives the story through the service functions the routes call (`giveConsent`, `declareGender`, `savePreferences`, `setPondOfAccount`, `saveProfile`, `onboardingStatus`, `eraseAccount`). The persona's first real login at a test bank then finds the identity by the same hash and resumes the live account (`features/identity/bank-login.feature`, "A second login of the same person resumes the live account"). The code exists in the job's memory for the derivation and in no line it writes; the key leaves nothing (rule 2). The job's lines carry keys and counts.
3. **The job cannot run anywhere but staging's container, by what the process was given.** `assertStagingProcess`: `APP_ENV` is `staging`, and none of `DATABASE_URL`, `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_APP_PASSWORD`, `HETU_HMAC_KEY`, `SSM_PARAMETER_PREFIX` is in the process's environment: the database and the key come from the parameter store the container's role reads, never by hand. A laptop that sets `APP_ENV=staging` reads staging's parameters through the maintainer's session and reaches no database (the address is the VPC's); one that tunnels gives a `DATABASE_URL`, and is refused. `assertDemoTarget` then asks the server that it is a managed one. Production refuses by the first word: its container has `APP_ENV=production`, and a test runs the job so and sees nothing written. What no question to the server can tell is staging's server from production's (both managed, both called `kuutti`, ADR-014 §11); the process's rule is what tells them apart. The guard is against accidents, a tunnel, a pasted key, the wrong window: a holder of the maintainer's own cloud session can read staging's parameters anyway, and nothing here pretends otherwise.
4. **`demo:population` and `demo:reset` run on staging the same way.** `--env staging` from inside the container: the population's writer is unchanged (ADR-014 §9 marks it; one pond, #146, sized over the gate, over the majority share, every counter cell at ten or more); the reset forgets the personas by the hashes the container derives (`personaHashes`), not by the mock bank's marks, which mean nothing on staging, and gives the stories anew through the services. Both read the configuration as the job does and refuse as the job refuses. After either, and after the stories, the counter of #54 is counted anew, which ADR-013 forbids in a deployed environment: nobody on staging is anybody, so the exception is staging's.
5. **The story is one, the hands are two.** `giveHistory(history, writer)` takes a `HistoryWriter`: `viaRoutes` logs the persona in at the mock bank and calls the routes (the local reset, unchanged in what it does); `viaServices` registers and calls the services (the job). The two direct writes no route makes (an older wording of the terms, a ban) name the account and, beside it, the persona's identity as the writer knows it: by the mock bank's marks locally, by the hash on staging. On a later run of the job a live account is resumed and its story not retold, and a story that ends in a ban or a deletion refuses the login as the callback would refuse the person, which the job takes as the story told already; so a second run changes nothing, and a story half told (a job that stopped midway) is mended by the reset, which forgets the persona and tells it anew. After the waiting time of a deletion (thirty days) the callback's rule lets the deleted persona register again, and so does the job: her story is told once more and she is erased once more, with one more deletion counted, as a person's would be.
6. **The personas on staging are marked as the population is, and found as a person is.** The identity row the job writes carries `kuutti-demo:<key>` as its subject and no time of authentication (ADR-014 §9: no bank was involved); unlike the population's, its hash is the code's, so the bed's login finds it, and a login then writes the broker's reference over the mark, as every login does. Nothing reads the mark to decide anything; the reset finds the personas by their hash.
7. **The image carries the demo commands as files of their own.** ADR-014 §10 kept the demo tools out of the API's image; they are in it now, as `dist/demo-stories.js`, `dist/demo-population.js` and `dist/demo-reset.js`, each bundled on its own, so nothing of the demo is on `dist/index.js`'s import graph (the linter still refuses `@kuutti/db/demo` in the apps' own code). Production's image carries the same files; every one refuses there by §3.
8. **Moderation is on for staging** (`moderation=rekognition` under `/kuutti/staging/`, the instance role's two detect calls, #49), so the moderation queue is part of the demo once #142 brings the negatives.

## Consequences

- `apps/api/scripts/demo-stories.ts`, `apps/api/scripts/demo/services.ts` (+ `demo-stories.test.ts`), `giveHistory` over a writer in `apps/api/scripts/demo/histories.ts`, `resetPersonas` with a hash selector, `--env staging` in `demo-reset.ts` and `demo-population.ts`, `assertStagingProcess` and `staging` in `DEMO_ENVIRONMENTS` (`packages/db/src/seed/command.ts`), `deriveArtificialIdentity` and the registration's three repository functions exported from the identity slice, `saveProfile` from the profile slice, the three entries in `tsup.config.ts`. No table, no route, no event.
- The identity slice exports a derivation for the first time. It takes only an artificial code, and `hetu.ts` says so; the callback's derivation stays inside.
- `pnpm demo:stories` exists on a laptop so that the file is typechecked and tested like the others; it refuses there, by §3.
- A persona's first login on the bed overwrites the job's mark with Telia's transient `sub` and the bank's method (ADR-016: every login refreshes the reference). That is right: the row is then a login's, as everybody's is.
- For #142: the photos of the stories go through `uploadPhoto` in the job, as the issue says; the writer gets a `photos` step then.
- For the maintainer: `infra/README.md` says how to reach the container (an SSM session and `docker exec`, or Dokploy's terminal for the `api` application) and the three commands; nothing of this needs a parameter written by hand.
