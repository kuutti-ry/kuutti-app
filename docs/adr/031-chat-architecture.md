# ADR-031: The chat's architecture: own sockets and tables, a Matrix homeserver, or a hosted service

- Status: proposed (nothing is built; the decision is the maintainer's before #101 starts, as its comment of 2026-10-10 asks; §5 is the lean, and the points under "Open, the maintainer's" are his)
- Date: 2026-10-17
- Follows: TD-1 (a message belongs to the conversation), TD-3 (one box, in-process state, no Redis), TD-5 (events never carry text), TD-7 (the erasure table: the counterpart's message copies are kept), ADR-007 §4, ADR-011 §3 and §8, ADR-022 §4 and §5, ADR-024 §6, ADR-030 §2, §4 and §8, CLAUDE.md rules 5 to 9, "Security and privacy defaults", "Code" and "Decisions", `.claude/rules/api.md` (WebSockets), `docs/security-checklist.md` (WebSocket messages through zod); issues #101, #84, #100, #102, #103, #104, #105, #83, #106, #311, #312

## Context

Olli's input of 15/09/2026, as #101's comment of 10/10/2026 records it: build the chat on an existing messaging platform such as Matrix, "a mature server-side implementation out of the box", with a client SDK that carries the state machine and leaves only the UI to us. The comment asks for this record before the milestone starts, both options costed against the rules we already have: a homeserver is one more service on the one box with its own store and identity namespace; end-to-end encryption conflicts with the frozen conversation of #84; the erasure table must map onto rooms and redactions; the homeserver logs for itself; moderation runs through two systems; and rule 8 closes federation and the client API to everything but our API.

On 17/10/2026 the maintainer asked whether an in-between exists: a JavaScript or TypeScript library that does chat, reporting and the rest, lighter than a homeserver. None does. What exists is of four kinds. Hosted chat services with SDKs (Stream, Sendbird, Twilio Conversations, TalkJS, CometChat): conversations, delivery, receipts, presence and moderation tools, with the message text on the vendor's servers. Full servers in other languages: Matrix (Synapse in Python; Tuwunel and Continuwuity, Rust single binaries over RocksDB, the two continuations of conduwuit, which was archived in April 2025; Dendrite in Go), XMPP (Prosody, ejabberd), Tinode (Go, GPL-3.0, self-described beta) Rocket.Chat (Node, but a whole product on MongoDB) and Ethora (a Node layer over ejabberd; Alternatives considered). Transport libraries in TypeScript: Socket.IO (rooms, acknowledgements, a buffer across a reconnect, connection state recovery) and `ws`, which `@hono/node-ws` wraps, the thinner one. React Native UI kits: react-native-gifted-chat, in maintenance mode by its maintainers' word, and Flyer Chat's React Native package, unmaintained. Nothing gives chat semantics as a module to embed in our process against our tables.

That is because every rule the chat has is a join against Kuutti's own tables, whatever carries the bytes: who may write to whom is the match (#100) less the blocks (ADR-030 §2), the sanctions (ADR-024 §6) and the break (ADR-022); what a message may say is the plain-text rule that refuses contact details (#103); what erasure keeps is TD-7's kept side (ADR-007 §4); what a report freezes is ADR-030 §4's table, read by #312 behind an audit row; what a push may say is #102's; what #105 counts is per account. A platform carries the bytes and holds the text; the rules stay in our handlers. So a platform saves the transport, which is the small part, and adds a second store of the text to keep in step with ours, which is the large one.

## Decision

1. **Three options, one list.** Each is costed against the same rows: CLAUDE.md's rules 5 to 9, TD-7, ADR-030 §2, §4 and §8, the issues that depend on the chat, the one box (TD-3), a new dependency's maintenance, pinning and licence under `scripts/license-policy.json`, and a new recipient under "Who else handles your data" in the privacy policy, whose table today names Amazon, Telia, Sentry and Expo and then says "Nobody else".

   | Rule 7, only matched, unblocked, unsanctioned people write | the match, the block and the sanction mirrored into room membership: two stores, no shared transaction | the same against the vendor's API, over the network | the match row, `blocked_between` and the state in the send's own statement |
   | Rule 8, no web surface, no CORS | the client API answers any origin, as the spec asks: closed, unless the phone talks to it; then our API proxies it, and the SDK's state machine runs against us | the vendor's API is a web surface by design, reached from the phone with a token we mint | one WebSocket on the API, under the session guard |
   | Rule 9, secrets | the homeserver's own config file holds its secrets, outside SSM unless templated at boot | one API key in SSM | nothing new |
   | TD-7, the counterpart's copy under "deleted user" | a redaction deletes for both; the kept side is a deactivated user, and what the server still holds of one is unmeasured | the vendor's deletion, with its own choice of what stays | the sender's link nulled, the row kept |

   | #102, a push with no text or name | Matrix pushes through a gateway, and Sygnal speaks APNs and FCM, not Expo: a gateway of ours, pushers set to `event_id_only` | the vendor's push with our native credentials uploaded to them, or their webhook and Expo from us | our API, Expo, "there is a message" |

2. **A, a Matrix homeserver, and what is unknown.** Tuwunel or Continuwuity, not Synapse: Synapse is the one the fear in #101's comment names, Python on PostgreSQL, memory-hungry, AGPL-3.0 since 1.99. Federation and registration off; the client API on localhost; no end-to-end encryption, since the frozen copy and #312's reading of it need the server to read the text, and the box is the association's, as ADR-011 §8 reasons. Our API mints a Matrix user per account (an opaque localpart, never the account id, which would otherwise sit in every event the counterpart keeps), holds its access token and the mapping in a table of ours, and deactivates the user at erasure. A message is one event in a room shared by both, so TD-7's shape, the sender's link cut and the words kept for the counterpart, is not a redaction, which removes the content for both and which Synapse keeps for days afterwards; it is a deactivated user, and what the server still holds of one is to be measured. Unknown, and said as such rather than guessed: the memory and CPU of a Rust homeserver at five thousand people; its retention of redacted content and what its logs carry at the level we would run; the cost of RocksDB backups beside RDS's snapshots; the client, since matrix-js-sdk targets web and Node and matrix-rust-sdk's official bindings are Swift, Kotlin, JavaScript and Node, none for React Native (a community UniFFI generator for React Native exists, one person's project, and `@unomed/react-native-matrix-sdk` is built on it; neither is Element's), so "only the UI left to us" does not hold on Expo either: the state machine on the phone would be ours, or an unofficial binding's; and the maintenance of a homeserver whose lineage was archived this year. Each is work to learn before a line of chat is written, which is the costing's point: the unknowns are all on this side.

3. **B, a hosted service.** Stream, Sendbird, Twilio Conversations, TalkJS and CometChat are the same shape: the text lives on their servers, the vendor becomes a processor under a data-processing agreement and a row in the policy's table with its own sub-processors, and the region is what they offer. CLAUDE.md's "never paste user data or secrets into any external service" is the rule a chat service exists to break, for every message. The price is per monthly active user with free tiers under the vendor's terms, which change; a free non-commercial app has nothing to carry it but the association's budget (TD-4). And every rule in the table is re-implemented against the vendor's API anyway: a match creates a channel, a block freezes it, erasure deletes the vendor's user and takes what their deletion takes, the frozen copy is their export, the push is theirs or ours through their webhook, #105 is their hook. What is bought is a maintained React Native SDK and UI kit, whose accessibility and three languages are ours to verify all the same.

4. **C, the own build, and the transport facts that matter.** `@hono/node-ws` in the API's one process, the conversation, participant and message tables in Postgres, presence in memory, every socket message through a zod schema from `packages/schema` (`docs/security-checklist.md`), the socket authenticated at the upgrade by the session and every query scoped by its account, application-level ping and pong (rules/api.md), LISTEN/NOTIFY fan-out only if a second instance ever exists. Socket.IO was weighed for its reconnect machinery and does not change the design: its connection state recovery (since 4.6.0) exists on its built-in in-memory adapter and not on its Postgres adapter, its documentation says it "will not always be successful" and that the application must still synchronise the two sides, and its client's buffer of sends across a reconnect doubles a message whose acknowledgement was lost. So resume and idempotency are the application's with either library, and the thinner one stays, with React Native's own WebSocket on the phone, unless a named need appears.

5. **The lean: C, with this design.** For the maintainer to confirm or overturn. Every message carries an id the phone generates, and a unique index on `(conversation_id, client_id)` makes a resend after a lost acknowledgement the same row, answered with what was stored: nothing is doubled. Every message takes a sequence number per conversation, assigned in the insert under the conversation row's lock, so order is total and a gap is visible. Postgres is the store and the socket is the notifier: a message is sent when committed, pushed to the counterpart's live sockets, and said through Expo (#102) when there are none. Resume is the client sending, at every connect, the last sequence number it holds per conversation, and the server replaying from Postgres what is newer, in order: nothing is lost, and a restart of the process costs the presence map, which the reconnects rebuild. Read receipts are a `read_up_to` sequence on the participant row, fanned out over the socket. The send's statement joins the match, `blocked_between` and both states (rule 7, ADR-030 §2, ADR-024 §6, ADR-022), so a block that lands while a message is in flight refuses it. Erasure nulls the sender's link and keeps the row, under "deleted user" (TD-7, ADR-007 §4), and the frozen copy is a copy of these rows (ADR-030 §4). Length and rate are `matching_config` rows (Open, 3).

## Consequences

- Nothing changes in the code with this record. #101 builds §5; its own record for the tables and the retention of messages (its "Done when") settles what this one leaves: how long a conversation's words are kept after its match is archived, whose words the person's export carries (one's own, or the thread, as ADR-007's comment on #101 asks), and what the counterpart sees of a paused chat (ADR-022). The `conversation` source and the frozen copy's table of ADR-030 §4 land with it.
- `@hono/node-ws` is new to `apps/api` (MIT, over `ws`, by the Hono maintainers, pinned); nothing new on the phone. No new recipient; Expo is #102's.
- Left out of C on purpose: a second instance (presence in memory, fan-out by LISTEN/NOTIFY when one exists, as rules/api.md already says; §5's resume does not depend on it, since Postgres is the store); federation or bridging with anything, which rule 8 and the product constraints forbid; media in messages (#101's out of scope; rule 4 would route it through the pipeline); end-to-end encryption, which the frozen copy excludes; a "delivered" state beyond sent and read; editing or unsending a message, which TD-1's "a message belongs to the conversation" argues against and the maintainer may want anyway.
- What would make A needed: federation or bridging with other Matrix users, or a second product of the association sharing the chat; end-to-end encryption as a requirement, with the frozen copy given up. What would make B needed: features (media, reactions, threads, moderation tooling) wanted faster than they can be built, with a budget for them and the policy's "Nobody else" given up. A second instance, on its own, needs neither: C fans out through Postgres.

## Alternatives considered

- **A.** Not chosen: a second surface or a proxy of the client API, a second store of the text with its own retention and logs, and every unknown of §2 on its side, for a transport that §5 gives in a few hundred lines.
- **B.** Not chosen: the message text leaves the box to a paid processor, against CLAUDE.md's rule and the policy's "Nobody else", and the rules are re-implemented against their API anyway.
- **Socket.IO over `@hono/node-ws`.** Resume and idempotency are the application's either way (§4); it adds a client dependency on the phone and rooms we do not need. Revisited if a named need appears.
- **Server-sent events.** Rejected in #101: presence and receipts need a connection that goes both ways.
- **A React Native chat UI kit.** react-native-gifted-chat is in maintenance mode by its maintainers' word, its fork `@kesha-antonov/react-native-chat` is one person's, and Flyer Chat's React Native package is unmaintained. The accessibility rules (every touchable labelled, 44 points, buttons not swipes, OS font scaling), the i18n rule (keys, three languages) and the theme's tokens are ours to verify in a third party's components; a list and an input are what the screen is, so a kit saves less than it costs to audit.
- **Ethora.** The one assembled product found: it markets itself as a self-hosted Stream or Sendbird alternative with a React Native SDK, and is a Node API layer over ejabberd (XMPP) with custom services, so A's shape in another dialect with two more processes. Its SDKs are AGPL and MIT, and its server, Ethora Core, is under a licence of its own with an enterprise EULA and commercial licences from its company: an AGPL SDK in the mobile bundle without a store permission of its own takes the store distribution away again (`scripts/license-policy.json`, `LICENSE-EXCEPTION`), and a server licence that is not open source is outside the policy altogether. Not a candidate.
- **XMPP, Tinode, Rocket.Chat.** A's costs in another dialect, with less of a client story for React Native.

## Open, the maintainer's

1. Whether Olli's input changes the lean: the two things it buys, a maintained state machine and federation, are a second surface (§2) and a feature we never want. The decision is his, before #101 starts.
2. Whether a Rust homeserver is worth a second costing once the chat exists, with measured numbers in place of §2's unknowns.
3. `message_max_length` 2,000 and `messages_per_minute` 60 as `matching_config` rows, #101's proposed values, born in a migration with the seed (rules/db.md).
