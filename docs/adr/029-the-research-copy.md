# ADR-029: The research copy: Parquet on S3, the copy's census, and the researcher's read-only role

- Status: proposed (the app half, §1 to §7 and §12, is built as written here; the infra half, §8 to §11, is a pull request of its own that the maintainer applies; the points under "Open, the maintainer's" are his, and the status changes when he has answered them)
- Date: 2026-10-17
- Follows: TD-5 (research use of events, never text), TD-4 (AWS in eu-central-1), CLAUDE.md rules 5 and 6, ADR-011 §6, §8 and §9 (the retention, nothing streams anywhere, what makes the block anonymous), ADR-005 (the media bucket), ADR-001 (Identity Center), ADR-004 §3 (what a preview is trusted with), ADR-018 (staging holds invented people), ADR-021 (tests at every level), `.claude/rules/api.md` (nightly jobs: events to Parquet, retention pruning), `.claude/rules/infra.md` (S3 lifecycle, access logging on the research prefix); issue #194

## Context

The research events (ADR-011) live in a partitioned table that keeps them for at most ninety days, the promise of the binding research text. The research partner needs the block for longer and outside the operational database, which ADR-011 §8 left to a change of its own, and §9 set the rule every such copy follows: a cell of pond, age band and snapshot under k = 10 is generalised before it leaves, the snapshot's fields first, then the age band to its neighbour, then the pond, and dropped if still under k. #194 asks for the pipeline: a nightly job writing the events to Parquet under `research/` on S3, one file a day keyed by `research_id` only, the prune of rows older than ninety days, Glacier Instant Retrieval after twelve months, and a read-only role for the researcher with access logging. The maintainer split it on 2026-10-17: the app half (the job, the prune, this record, the docs) and the infra half (the role, the lifecycle, the logging), applied by him.

Three things in the code shaped the decision. The prune was already built (ADR-011 §6), keyed on a month's first day so that no row outlives the promise. The census of §9 as written counts the live table, which leaks across the copy's files (§4). And a pull-request preview runs under staging's instance role with staging's bucket name in its configuration (ADR-004 §3, `lib/config.ts`).

## Decision

1. **Once a day, one file per UTC day, in the media bucket.** The nightly job `research-export` runs inside the API process (rules/api.md), immediately before `research-events-partitions`, where §12 says: on staging and beside a developer's stand-in, not in production yet. It writes `research/YYYY/MM/YYYY-MM-DD.parquet` into the environment's media bucket (`kuutti-media-<env>-<account>`, ADR-005) through the S3 client of `lib/s3.ts`; no new configuration key. The day is UTC, as the partitions are, so the month folder is the table's partition and the name survives a flat sync. A run writes every missing day from the oldest partition's first day to the last closed day, in ascending order; a day closes an hour after it ends, since an event stamped 23:00 may commit a moment after midnight, and the night runs at 04:00 in Helsinki, one or two hours after midnight UTC. A day without events is a file with the whole schema and no rows: a missing file means a missed night, an empty one means nothing happened. A second container finds the run's advisory lock held (`pg_try_advisory_xact_lock(725121151)`) and leaves the night to the first.
2. **The file, format `research-events/1`.** Flat columns, one row group, SNAPPY, statistics on:

   | Column | Parquet | Note |
   |---|---|---|
   | `at` | INT64 TIMESTAMP(MILLIS, UTC), required | already truncated to the hour (ADR-011 §1) |
   | `name` | UTF8, required | a registry name |
   | `research_id` | UTF8, required | the pseudonym, 36 characters; text rather than the UUID type, so pandas reads a string |
   | `consent_version` | UTF8, required | the wording the person had accepted |
   | `pond` | UTF8, optional | the slug; null when no pond was chosen; `*` when withheld |
   | `age_band` | UTF8, required | one of the six bands, or `18-29`, `30-39`, `40+` when coarsened |
   | `gender` | UTF8, optional | self-declared; null when not declared |
   | `field_<key>` | UTF8, optional | one per profile field flagged `research` (`field_intent` today); null when unanswered; `*` when withheld |
   | `props` | BYTE_ARRAY JSON, required | the props as the registry's strict schema parsed them, keys sorted |

   The key-value metadata names the format, the day, k, the census rule, and how many rows were dropped and how many were unreadable. Withheld is `*`, not null as §9's "the pond to null" had it: null already says "not chosen" or "not answered", and a researcher must tell the two apart. The rows are ordered by hour, name, pseudonym and props, never by insertion: within the hour the order of writing would say which event came first, which the truncation of `at` exists to hide. The same rows give the same bytes. A change of the format is a new format version, fixed forward; a day is never rewritten.
3. **What the copy never carries** (rule 5): the account, the event's own id, the stored snapshot (only the research fields, through `researchFieldsOf`, so a key the registry dropped never reaches a file), and any text. Every row is read again through the registry: a retired name, props the strict schema refuses, a band or a gender outside the closed lists make the row unreadable, and it is left out and counted. A test decodes every column of every file written over real accounts and events and finds no account id, no event id and none of the texts planted in the rows.
4. **The copy's census counts what the copy released (amends ADR-011 §9).** A cell is one value of pond, age band, gender and the research fields; its size is the number of distinct pseudonyms that carry exactly that value in the copy's files of the previous ninety days and in the day being written, and whose research consent is live on the night the file is written: a `research_subject` row exists for them, read once a run. An account has at most one such row, so a live pseudonym is a person and k counts people. A withdrawn or erased person's pseudonym counts for nobody: one person who gives, withdraws and gives the consent again leaves a fresh pseudonym behind each time (`CONSENT_CHURN_PER_DAY` allows ten a day, as many as k), and those cannot carry a cell to k; a pseudonym withdrawn since an earlier file stops counting there too, so a later file can withhold a value an earlier one released. For each day, in order: a cell of at least k is released as it is; under k, the research fields are withheld; then the age band goes to its fixed pair; then the pond is withheld; what is still under k is dropped and counted. Every value the copy releases was carried, on the night its file was written, by at least k people whose consent was live, and since files are never removed it stays carried by at least k pseudonyms across the whole copy, for good; each day is a pure function of its rows, the files before it and the pseudonyms live that night.

   §9 as written counts the live table, and that leaks. Three people of a cell are released generalised in September; seven newcomers arrive in October; the table now holds ten of the cell, October's file releases it exactly, and across the files seven people carry that value. Counting what was released closes it, at a cost: early on less comes out, since a cell opens exactly only once k of its people are active on one day or the copy already carries it. Counting the window and not the whole copy is conservative (an older release no longer counts) and keeps the night's read to ninety small files. The pure cascade is the unit the property tests hold: every released value is carried by k pseudonyms that count, every row is released once or dropped, k holds across any sequence of days, and the order of the rows changes nothing; a census that counts every earlier release alike, whatever its value, fails the crossing case and two of the properties.

   What stays possible, for the maintainer to accept or close (Open):
   - **A withdrawn person can be found again, for as long as the copy is kept.** A withdrawal removes the mapping row but keeps the consent row, with the account and the exact time the research consent was given (`given_at`, the proof of ADR-010 §5; only erasure removes it, ADR-010 §14). The copy keeps the `research_opt_in` of that consent: its hour (`at`) and the whole days since registration (`sinceRegistrationD`), which the account row keeps too. Whoever holds both the copy and the consent table, which is the association, can join the two and in most hours finds one account, and through the pseudonym every event of that enrolment; `account_resumed`'s `afterDays` beside its hour is a second handle of the same kind. ADR-011 §1 accepted the join for the table's ninety days; the copy makes it last as long as the copy is kept.
   - **A generalised value can give away the finer one it hides.** k holds for each value as written, not for what the files let a reader work out. The cascade is a function of the files the researcher holds, of a rule each file names (`kuutti.census`) and of who withdrew, which the researcher does not see; so a row generalised while a sibling's finer cell is already open usually says which finer value it is not. When the copy carries `40-49` for k people of a pond and a gender, a person of that pond and gender who comes out as `40+` is `50+`, and `50+` may be carried by fewer than k in the copy; the same goes for a field withheld as `*` once every other answer of that pond, band and gender is open. The sparse `50+` band makes this common, not a corner. `copy-census.test.ts` shows it ("a value generalised past an open sibling cell gives away the finer value it hides").
   - k holds per cell, not per trajectory, so one pseudonym's path through several cells is not generalised as a whole.
   - There is no l-diversity, so a cell whose k people all did the same thing says it of each of them.
   - `consent_version`, `at`, `name` and `props` are outside the cell.
   - Gender is never withheld, so a gender with fewer than k people in a coarse band is absent from the copy rather than hidden in it. A fourth step, the gender to `*`, is his call.

   The live census of §9 (`research-anonymity`) stays as the early warning.
5. **Written once, failing closed.** The put is conditional (`If-None-Match: *`): a file that exists answers 412 and stands, read as the day's for the census after it; the S3 stand-in honours it too. The API may not delete under `research/` (§9). A store or database error, a prior file that cannot be read, or a file of a day not yet closed (§12) stops the run before anything is released without its count; the night logs `nightly job failed` and the next one catches up on every day the table still holds. The job's line carries counts only: days written, rows read, released, generalised, dropped, unreadable.
6. **The prune stays as built, and checks the copy first.** ADR-011 §6 drops a month once its first day is ninety days old, so a row lives between about sixty and ninety days. The two readings #194's brief offered both break something: dropping a month only once every row is past ninety days keeps rows for up to about 121 days, against the binding text; deleting rows needs the §5 triggers bypassed. Where the copy is written, `researchEventsJob` is given `copiedBeforeDrop`: before a month goes, the copy runs once more and every day of the month must have its file; the days that do not are logged as an error, `research events dropped without their copy`, with their number, and the month is dropped anyway (P1: the promise wins over the copy). In normal operation this never fires: a month's last day is copied about sixty days before its partition goes. It fires when the copy has failed every night for longer than that margin: about sixty days for a month's last day, ninety for its first, less for the oldest month the table holds on the first night. One way to get there that no offline check rules out: the instance role's write-once condition (§9) needs S3 to hand the `If-None-Match` header to an identity policy, which only the first night's write shows (`infra/README.md`, Research copy); if it does not, every put is refused, the alarm (§11) mails the first morning, and a month nobody fixes the copy for goes without its days. #194's brief asked that the prune never drop what was not copied; that holds only under P2, which keeps the month and logs every night until somebody fixes the copy, while its rows outlive the ninety days. Where no copy is written the prune is as it was.
7. **The library: `hyparquet-writer` 0.16.12 and `hyparquet` 1.31.4,** exact pins in `apps/api`. MIT; no install scripts; the writer's only dependency is the reader, which has none; pure ESM JavaScript, bundled by tsup into `dist/index.js` with nothing native on the arm64 image; the reader reads the earlier files for the census. Releases on 2026-09-22, 10-08 and 10-13. Rejected: `@duckdb/node-api`, a native binary of about 60 MB per platform the image would copy like sharp's `@img`, for one small file a day; `parquet-wasm`, which needs apache-arrow and a WASM blob of several megabytes; `@dsnp/parquetjs`, thirteen dependencies with thrift, brotli-wasm, bson and its own copy of the AWS SDK. The risk is a pre-1.0 writer from one organisation; flat columns and the read-back tests contain it. The tests read every file back with `hyparquet` and check the physical and logical types a reader goes by. That reader shares its author with the writer, so it is not an independent check: no reference reader (DuckDB, pyarrow) is installed on the machine the change was built on, and the maintainer runs the snippets of `docs/research/README.md` once against a staging file before the first handover.
8. **The bucket's lifecycle** (infra half). The same bucket, prefix `research/`; a rule moves the files to Glacier Instant Retrieval at 365 days. The bucket sets `transition_default_minimum_object_size = "all_storage_classes_128K"`, S3's default spelled out: a file under 128 KB stays in Standard. That is the cheaper side, since Glacier Instant Retrieval bills every object as at least 128 KB and each transition is a request; and `varies_by_storage_class` would not move it either, since it lets small objects reach Glacier Flexible Retrieval and Deep Archive only. Staging's files, with little in them, stay in Standard; production's are expected to pass 128 KB and move. No expiry is proposed.
9. **The API's rights on `research/`** (infra half, the instance role's inline policy): `s3:PutObject` on `research/*` only with `s3:if-none-match` `*`, so the API can never overwrite; `s3:GetObject` on `research/*` for the census; `s3:ListBucket` with `s3:prefix` `research/*`; no delete. Until it is applied, staging's export fails with AccessDenied every night and writes nothing.
10. **The researcher's role** (infra half): `kuutti-<env>-research-read` under `/kuutti/`, the permissions boundary, sessions of an hour; `s3:ListBucket` on the bucket with `s3:prefix` `research/*` and `s3:GetObject` on `research/*`, nothing else. Its trust names this account with `aws:PrincipalArn` like the Identity Center role of one permission set per environment, `KuuttiResearchStaging` or `KuuttiResearchProd`, so that staging's assignment opens nothing in production: `role/aws-reserved/sso.amazonaws.com/AWSReservedSSO_<set>_*`, and the same with one path segment for the region before the name, two patterns and no leading wildcard. Who the researcher is, is decided by the Identity Center assignment, and the trust never changes (the apply role cannot update a trust policy). What stays possible: the name is matched up to the provisioned role's suffix, so a permission set named `<set>_<anything>` would pass too; only the maintainer creates permission sets. Matching the suffix exactly (sixteen characters, as far as known) waits for a provisioned role's ARN to show it, since a wrong guess would lock the researcher out behind a trust CI cannot change. The alternative, if the partner has an AWS account of its own, is a cross-account principal with an external id.
11. **Every read logged** (infra half): a CloudTrail trail with data events for `AWS::S3::Object` under `<bucket>/research/` and log-file validation, into a bucket of its own; it records the researcher's reads and the API's writes. Not S3 server access logs, which are per bucket (every CloudFront media fetch with them) and delivered on a best-effort basis. An alarm on `nightly job failed` and on the prune's line (the observability module).
12. **Where no copy is written.** The job is wired only when media has a bucket: on staging and beside a developer's stand-in, never in a preview, whose media settings are dropped (`lib/config.ts`), and never where nothing is configured. Nor in production, for now: the copy keeps the `research_id` past the ninety days the research text promises (Open), so `boot.ts` leaves it out there, a `shortcut:` the maintainer's answer lifts, and production's prune runs as it did before the copy. The infra half composes `modules/research` in staging only, so production has no write right on `research/` and no researcher's role either; the change that lifts the shortcut adds it there. `boot.test.ts` holds all three. A preview's export would write into staging's `research/` under the shared role.

    What stays possible on staging once §9 is applied, the trust model of ADR-004 §3: code of a preview runs under the shared instance role, so it could read staging's `research/` and write a day the night has not written yet. The night refuses to go on past a file of a day not yet closed, since no night of ours writes one, and stays stopped (the alarm mails) until the maintainer removes the file, which the API cannot; a closed day the night has not reached yet (the hour or two between its close and the run, or a missed night) cannot be told from ours. Such a file stands as the day's for good: it is part of what the researcher copies down, its contents are checked only for the format's name, not against rule 5, and the census counts its pseudonyms as released, so invented carriers can open cells under k in the files of the ninety days after it. Staging's people are invented (ADR-018), and there are no previews in production.

## Open, the maintainer's

- **The ninety days of the binding text.** `legal.research.summary` (a DRAFT) says the events "are kept under a separate research identifier for up to 90 days". The copy carries the `research_id` and is kept for years; while a mapping row lives the association can join it to a person, so the copy is pseudonymised personal data in our bucket. Either the wording names a copy kept by the research partner (counsel's, a new consent version, with #208 and the DPIA of #190), or the copy drops the `research_id` past ninety days. Until he answers, production writes no copy at all, not only hands none over (§12); his answer lifts the `shortcut:` in `boot.ts`. Staging holds invented people only (ADR-018).
- **Re-linking a withdrawn person (§4).** Either the copy coarsens what joins, in the copy only: `sinceRegistrationD` and `afterDays` in bands, and the opt-in's `at` cut to the day (a new format version, §2); or a withdrawal coarsens the consent row's `given_at`, which is ADR-010's proof of the consent. Production writes no copy until the ninety days above are answered in any case.
- **P1 or P2 (§6).** P1 is built: the ninety days win, and a copy that fails for longer than the margin loses those days for good, the write-once condition of §9 being the one cause no offline check rules out. P2 keeps "never drop what was not copied", and rows outlive the ninety days until somebody fixes the copy.
- **The census's inference (§4).** Accept it, with the DPIA naming it; or close it: generalise a row to a coarser value only where some other value under that coarser value would also have been refused at the finer level, and drop the row otherwise. Closing it releases fewer rows, of `50+` most, from the day it lands; the files already written stay as they are.
- The census of §4, or §9 as written (about forty lines fewer and more rows released, with the leak §4 describes). Either way it amends his accepted ADR-011 §9.
- The gender as a fourth step (§4).
- How long the copy lives (no expiry proposed) and how long the access log is kept (five years proposed).
- Identity Center for the researcher, an extension of ADR-001's click-ops exception for a permission set and an assignment, or a cross-account trust (§10); a source-address condition on the role; the trust matching the provisioned role's suffix exactly, once an ARN shows its length (§10).
- The reference readers' check (§7).
- The admin panel's researcher role keeps no screen: the copy is read through AWS. The `admin.forbidden` text and the comment "until #194" in the panel can say so.

## Consequences

- `apps/api/src/research/`: `copy.ts` (the job and the check before the prune), `copy-census.ts`, `copy-file.ts`, `copy-store.ts`, with tests at each level (property tests on the census, the file read back, the store against the stand-in, the job against Postgres). `partitions.ts` exports the partition listing and the months due, and its job takes the check. No migration, no contract change, no configuration key.
- The nightly jobs gain `research-export` before `research-events-partitions` wherever media has a bucket, production excepted until the ninety days are answered (§12); a developer's stand-in gets `research/` files too.
- `docs/research/README.md` is the researcher's: the columns, the sentinels, k, the empty files, how to read them.
- The infra half (`infra/modules/research`, the media module's lifecycle rule and output) is #194's second pull request.
- On staging the copy holds what the invented people's sessions and the personas' stories emit, which is little: most files are empty, and most cells are under k.

## Alternatives considered

- **DuckDB in the container or a job of its own** (#194's first idea): a native binary or a second deployable for one small file a day (§7).
- **The census of the live table**, as §9 wrote it: rejected for the leak in §4.
- **A copy without the `research_id`**: no study of a person's path through the app, which is what the events are for; it is the fallback if the wording cannot change (Open, the maintainer's).
- **A bucket of its own for the copy**: one more bucket, policy and encryption set-up for what a prefix and a role scoped to it already separate; the media bucket is private and read only through the distribution (`media/*`) and, from §10, the researcher's role (`research/*`).
