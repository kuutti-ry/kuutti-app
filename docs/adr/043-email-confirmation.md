# ADR-043: Confirming the optional e-mail by a code

- Status: accepted 2026-10-21 (#385, built as written here on the maintainer's decisions of 20/10/2026, #385's comment; the SES identity in `infra/bootstrap` is his to apply and SES production access his to request; the points under "Open, the maintainer's" are his to confirm or change), amended 2026-10-25 by §5 (#450: the root's MX and SPF are Google Workspace's, the association's mailbox; see History) and by §5 and §6 (#385: the identity applied and the first code delivered; `noreply@kuutti.app` a Workspace alias; staging's testers `*@kuutti.app`; see History)
- Date: 2026-10-21
- Follows: TD-18 (no mail without a reason; the optional e-mail), TD-1 (the bank login is the only way in; the hetu key is for the hetu alone), TD-4 (one vendor, AWS, one account and one region), TD-7 (erasure), TD-19 (the parameter store and the instance role), ADR-007 (erasure and export, amended), ADR-018 (staging is the demo), CLAUDE.md rule 2 (the hetu key) and rule 8 (no web surface) and Product constraints (every tunable in `matching_config`); issues #385, #148, #196, #184, #387

## Context

#148 gave a person an optional e-mail address: hidden, never a login, and sent nothing (TD-18: no mail without a reason). It was called "a way back in", but a lost phone is a new bank login (#35), so #387 renamed it "a way to stay in touch". Before Kuutti writes to an address it has to know the address is the person's, since anybody can type anybody's. #385 asked how to confirm it with no web surface for the product (rule 8), and took the sending half's infrastructure from #196: SES, the domain's records, the instance role's permission and a record of bounces and complaints.

The maintainer decided on 20/10/2026 (#385's comment): a code, not a link; six digits, thirty minutes, three wrong attempts, as the first `matching_config` rows for it; the sending domain `kuutti.app`, whose zone is in Route 53 (`infra/bootstrap/dns.tf`); staging's personas confirm nothing unless one-time addresses come cheap. Five codes an account a Finnish day was set with the build, and the maintainer confirmed it as his number on 21/10/2026 (Open 1, settled).

## Decision

1. **What is confirmed, and why.** An address is confirmed when its person types the code Kuutti sent to it. An unconfirmed address receives nothing but its confirmation. A confirmed one receives nothing else yet either, since no other mail exists; what it may receive later, and under which consent, is #196's. Confirming is optional and holds nothing back: no screen, round or feature waits for it, and the address stays a way to stay in touch, never a login (TD-1) and never shown to anybody. `account.email_confirmed_at` (migration 0077) is when the code was typed. `GET /account/email` answers `AccountEmailResponse`: `{ email, confirmed, codeExpiresAt }`.

2. **The address.** `PUT /account/email` validates the address (`AccountEmail`, at most 254 characters) and answers `AccountEmailResponse`. A different address is unconfirmed, and the code waiting for the old one goes, in one transaction (`setEmail`, `apps/api/src/identity/repo.ts`). The same address, character for character, changes nothing, its confirmation included. `DELETE /account/email` (204) removes the address with its confirmation and its code. `PUT` sends nothing: the app's card asks for a code (`POST /account/email/code`) right after a save, so a send that fails never fails the save. Several accounts may give the same address; each confirms its own.

3. **The code.** Six digits (`EMAIL_CODE_LENGTH` in `packages/schema`, a format and not a tunable) from the operating system's generator (`randomInt`), zeros in front. No link: a link that opens the app needs #184's verified links, since few mail clients open a `kuutti://` link, and a link to a page of the API is a web surface (rule 8). What is stored is the SHA-256 of the account id and the code (`email_code`, one row per account, with its end and its wrong attempts), compared in constant time. Never the code, and never an HMAC with the hetu key, which is for the hetu alone (rule 2). The account id in front tells two accounts' equal codes apart.
   - **Sending.** `POST /account/email/code` sends a fresh code to the stored address and replaces any code that waits, its attempts back at none. A code works for `email_code_minutes` (30) and `email_code_attempts` (3) wrong tries. An account is sent at most `email_codes_per_day` (5) codes a Finnish day, counted from `email_send` under the account row's lock. The three numbers are `matching_config` rows (migration 0078, the seed the same), changed in the panel (#305). The send happens inside the transaction that counts it and stores the code, so a send that fails rolls both back: no code waits that never left, and the day's count is not spent on it.
   - **Its answers.** 200 with when the code stops working; 409 `email_none` (no address) or `email_confirmed`; 429 `email_code_budget_exceeded` with `Retry-After` until midnight in Finland; 503 `mail_unavailable` where `MAIL` is off or SES refused the message, with nothing written or counted.
   - **Confirming.** `POST /account/email/confirm` with `{ code }`. The right code confirms the address and the code goes. Anything but six digits is 400 `validation_failed`, before anything is read. A wrong code is 400 `email_code_wrong` with `attemptsLeft` in the detail; the third is 409 `email_code_spent`, and the code goes. 409 `email_code_none` when no code waits (none was sent, or the address changed since), `email_code_expired` past its minutes (the code goes), `email_none` with no address. A confirmed address confirms again with 200, so a second tap or a second phone reads the same answer. A refusal is answered after its transaction commits, so a wrong try counts.
   - **The message.** Plain text in UTF-8, in the request's language, three paragraphs of `messages.yaml` (`mail.emailCode.*`, `mail.signature`): the code and its minutes; that someone added the address in the Kuutti app to stay in touch, and to ignore the message if that was not them; "Kuutti ry". It names nobody, since the address may be somebody else's, and carries no link and no postal address. An HTML version in Kuutti's style is to come beside the text (Open 8).

4. **Where mail goes.** `MAIL` (`apps/api/src/lib/config.ts`) is `ses`, `log` or `off`. Unset, it is `log` in development and test and `off` everywhere else. Staging and production set `ses` through the parameter store's `mail`, as they set `moderation=rekognition`. A preview reads staging's parameters (`infra/README.md`, Previews), so a preview sends through SES too. `log` is refused at boot outside development and test: the log mailer writes the message, code included, to the log so that a developer can type it, and a deployed log is no place for a code. `off` sends nothing, and the code route answers 503 before it writes. `MAIL_FROM` is the sender, `Kuutti <noreply@kuutti.app>` by default. Mail leaves only through `Deps.mailer`, which boot builds with `mailerFor` (`apps/api/src/lib/mail.ts`). Tests hand in a double that records the message; no test reaches the network.

5. **SES.** One identity for the domain `kuutti.app`, in `infra/bootstrap` beside the zone's DMARC, since it belongs to no environment. The client uses the one region (`S3_REGION`, TD-4).
   - **DKIM.** Easy DKIM, its three CNAMEs in the zone. It signs as `kuutti.app`, so DKIM aligns with the From address under the zone's `adkim=s`.
   - **MAIL FROM.** `mail.kuutti.app`, with an MX to `feedback-smtp.<region>.amazonses.com`, where bounces return to SES, and the SPF `v=spf1 include:amazonses.com -all`. The envelope sender is that subdomain, so the root's own MX and SPF are not SES's to set. Since 2026-10-03 they are Google Workspace's, which holds the association's mailbox, `admin@kuutti.app`, and sends from it: the MX `1 smtp.google.com` and the SPF `v=spf1 include:_spf.google.com ~all`, with Google's DKIM key at `google._domainkey` (#450). Before that the root had a null MX and `v=spf1 -all`, since nothing received mail there.
   - **DMARC.** The zone's `p=reject; adkim=s; aspf=s` stays. SPF passes for `mail.kuutti.app` but does not align under `aspf=s`, so DKIM alone carries DMARC, which is enough for mail that SES signs. The Workspace's mail aligns both ways: its envelope sender is the sender's own address at `kuutti.app`, and Google signs as `d=kuutti.app`. Since the root's SPF names Google's servers, any message they send with a `kuutti.app` envelope passes DMARC on SPF alone, signed or not. That part of the protection rests on Google refusing such an envelope to its other customers. The root's SPF ends in `~all`, Google's advice: DMARC does the rejecting, and a receiver that refuses a hard SPF fail outright never sees that a forwarded message's DKIM still passes.
   - **Permission.** The instance role may call `ses:SendEmail` on that identity only, and only from `noreply@kuutti.app` (the condition `ses:FromAddress`). A `MAIL_FROM` of any other address is refused by IAM and answered 503. Staging's role may also mail only its testers (the condition `ses:Recipients`, §6); production's names no recipients.
   - **Bounces and complaints.** The account-level suppression list, for `BOUNCE` and `COMPLAINT`: SES itself stops writing to an address that bounced or complained. That is the record AWS asks about before it grants production access. #196 extends it with the events and Kuutti's own list. It holds Kuutti's own addresses too: on 2026-10-25 a code to `noreply@kuutti.app`, sent before its alias existed, bounced, and SES dropped every later message to it, for both environments, until the address was taken off by hand (`infra/README.md`, Mail).
   - **The sandbox.** A new SES account sends only to verified addresses and domains, at most 200 messages a day. Production access is the maintainer's request to AWS, for one account and one region. Kuutti has one AWS account (`infra/README.md`), so staging and its previews leave the sandbox together with production. From then on, only §6's list keeps staging from mailing anybody.

6. **Staging mails its testers alone, and its personas stay unconfirmed.** Every account on staging is one of Telia's pre-production test persons (ADR-018 §1), whose credentials are published (`docs/vendors/telia.md`), so anybody can sign in there as each of them and ask for five codes a day per identity, to addresses of their choosing. Out of the sandbox, those messages would leave from `noreply@kuutti.app`, signed as `kuutti.app`, through the account and region production shares: their complaints would count against production's sending reputation and fill its suppression list, and enough of them gets SES paused for production too. The sender condition of §5 does not stop that.
   - **The list.** Staging's instance role may send only when every recipient matches its list: the condition `ForAllValues:StringLike` on `ses:Recipients`, from the compute module's `mail_recipients`, which production leaves null (no limit). CI passes the repository variable `MAIL_TESTERS`, a JSON list of the testers' addresses, where a pattern such as `*@example.fi` is allowed. Unset, the list is Kuutti's own sender, `noreply@kuutti.app`, an alias of a Workspace mailbox since 2026-10-25, and staging mails that alone. Since that day the list is `*@kuutti.app` (Open 7). A send to anybody else is refused by IAM (`AccessDenied`, which the mailer reports as `MailFailed`) and answered 503 `mail_unavailable`, with nothing written or counted. A pull request's preview runs under staging's role, so the list holds it too.
   - **The personas.** In the sandbox SES delivers to any address of a verified domain, so a persona could be given a one-time address under `kuutti.app`. Reading its code would need SES receiving: an MX for a subdomain and a receipt rule that stores the message, if the region receives mail at all, and a step in the reset that reads it. That is a second mail path to show one card, and the maintainer allowed leaving it out. The personas have no address. A tester who wants to see the flow on staging gives an address at `kuutti.app`, which the list matches and the sandbox delivers to; an address elsewhere the maintainer adds to `MAIL_TESTERS` and, while the account is in the sandbox, verifies in SES.

7. **Records.** Neither the address nor the code reaches a log line, an error's detail, Sentry or an event. A send's line says that a code was sent, and names the account. A failed send is `MailFailed`, which keeps the SDK's error name and HTTP status alone, since SES names the address in its messages. The log mailer of §4 is the one exception, and it never runs deployed. The export carries `emailConfirmedAt` beside `email`; not the code's hash, its end or the sends. Erasure deletes `email_code` and `email_send` in its transaction (`deleteEmailRows`), and the tombstone nulls the address and `email_confirmed_at` (ADR-007, amended). `email_send` is a counter, not a history: a send deletes the account's sends of earlier days before it counts, so the table keeps the sends of the last day a code was sent, five at most, until the next send or the erasure.

## Consequences

- A person who mistyped the address learns it when no code arrives, and changes it. The wrong address got one message that names nobody.
- Anybody can give somebody else's address. Its owner gets at most five codes a day from each account that does, each naming nobody and asking only to be ignored. In production every account is a bank-verified person, but the cap is per account, not per address (Open 1). On staging every account is a public test identity, which anybody can use, hence its list of recipients (§6).
- Guessing: three tries a code and five codes a day are fifteen guesses a day at a million codes, from the account's own session. The hash keeps the code out of a read of the table, a snapshot or a query log. It does not stop somebody who holds the row from finding the code by trying the million, which is quick. The code works for thirty minutes and only from its account's session, so that reader gains little, and one who can write the table can set the confirmation anyway.
- The send holds the account row's lock for one call to SES, and another write to the account waits that long. A message SES accepted whose commit then fails carries a code that does not work; the person asks again. A stored code that never left cannot happen.
- SES accepts a message to a suppressed address and drops it, so the person is told a code is on the way and none arrives. Knowing which addresses are suppressed is #196's event destination; until then, a person who gets no code can give another address.
- An erased person's address stays on SES's account-level list if it bounced or complained: the list is AWS's, not a table of Kuutti's, and erasure does not reach it (Open 3).
- In the sandbox, a send to an address SES has not verified is refused and answered 503 `mail_unavailable`, with nothing written; on staging, sandbox or not, so is a send to an address its list does not match. Before the bootstrap was applied and SES had verified the domain (2026-10-25), every send was.
- A preview runs a pull request's code with staging's instance role, so it can send from `noreply@kuutti.app` to the addresses of staging's list. Write access is that trust (ADR-004 §3), as for the rest of the role.
- Trying the flow on staging takes the maintainer: an address joins `MAIL_TESTERS` and a staging apply follows (`infra/README.md`, Mail). A pattern in the list opens staging to every address it matches: with `*@kuutti.app`, every address of the domain, made-up ones included, whose bounces count against production's reputation (Open 7).
- A forwarder that breaks the DKIM signature makes the message fail DMARC, and the receiver rejects it. The person can ask for a code at the address itself.
- Development and tests send nothing: the log mailer writes the message to the API's log, which `pnpm env:up` shows.

## Alternatives considered

- **A link that opens the app:** needs the universal and app links of #184's native batch, since few mail clients open a `kuutti://` link. A code works in every mail client and on the web preview.
- **A link to a page of the API that says "confirmed":** a web surface for the product, against rule 8.
- **Storing the code itself:** readable in every read of the row, a snapshot or a query log, for as long as it works. Its hash costs one line.
- **An HMAC with the hetu key:** that key is for the hetu and nothing else (rule 2). The code needs no secret, only not to be stored as typed.
- **Sending on `PUT`:** a failed send would fail the save, or be swallowed. The app asks right after the save and shows the send's own answer.
- **A third-party mail service** (Postmark, SendGrid, Mailgun and the like): another vendor holding the addresses, with its own key to keep in the parameter store and its own processing agreement, where SES is in the account already, under the instance role (TD-4).
- **A subdomain in the From address:** the maintainer chose `kuutti.app`; `mail.kuutti.app` is the envelope sender only.
- **SES receiving for the personas** (§6): left out.
- **Staging without mail (`MAIL=off`):** as closed as the list, but nobody could try the flow before production.
- **A second AWS account for staging's mail:** its own reputation, suppression list and sandbox, against TD-4's one account, for a few codes a day.

## Open, the maintainer's

1. Settled 2026-10-21: five codes an account a Finnish day is the maintainer's number (#385's comment); a new one is a new version in the panel. A cap per address as well, if ever wanted, needs something of the address stored with each send, a hash of it at least.
2. SES receiving for staging's personas, if confirmed personas are ever wanted on the demo (§6).
3. #196: a configuration set with an event destination for bounces, complaints and deliveries, its metrics and alarms, and Kuutti's own suppression list by hash; and whether erasure takes an address off SES's account-level list.
4. Whether the export lists the day's sends, as it lists the person's exports (ADR-007's History of 2026-10-13); §7 leaves them out as a counter.
5. The request for SES production access: it describes the mail, the handling of bounces and complaints of §5, and the volume. Followed in #196 since #385 closed.
6. The message's words in Finnish and Swedish, machine text until the native review.
7. Settled 2026-10-25: staging's testers, the repository variable `MAIL_TESTERS` (§6, `infra/README.md`, Mail), are `["*@kuutti.app"]`, the maintainer's choice over a list of named addresses, which the public repository's logs would show. Its ceiling: anybody on staging can ask for codes to made-up addresses at `kuutti.app`, which Google bounces onto the suppression list production shares; a list of addresses lifts it, or #196's event destination shows it. Once he asks for production access (Open 5), the list is what keeps staging inside the domain.
8. The message's HTML version, styled to Kuutti's brand, beside the plain text: #404 (milestone M5.5 Design). Nothing fetched when it is opened, no link, the words still from `messages.yaml`; it amends §3 when it lands.
9. In the sandbox SES may also check the role's permission against a recipient verified as its own identity, which `SesSendAsNoreply` does not name. If a send to such an address is refused with `AccessDeniedException`, the role's resource widened to `identity/*`, its sender and recipient conditions kept, lets it through. An address at `kuutti.app` does not meet it, and production access ends the question (#403).
10. The code's end time is shown in the phone's own clock (`EmailCard.tsx`), not in Finnish time: built so, his to confirm (#403).
11. An address removed on another phone: the card shows the empty form with no word of what happened. A line needs his English first, then machine Finnish and Swedish for the review (#403).
