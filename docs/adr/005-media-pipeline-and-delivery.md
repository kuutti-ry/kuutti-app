# ADR-005: Photo pipeline and delivery

- Status: accepted, amended 2026-10-18 (a second purpose: a photo sent in a conversation, #350) and 2026-10-22 (the image's third-party notices, #416; see History)
- Date: 2026-09-25
- Follows: TD-2 (S3 and CloudFront as the media path), TD-8 (photos are moderated, metadata-free, signed and time-limited), TD-4 (one vendor), TD-6 (exposure is counted), CLAUDE.md rule 4, `.claude/rules/api.md` Media, `.claude/rules/infra.md` CloudFront, audit F141; issue #48

## Context

A photo is the most identifying thing in the product and the easiest to scrape. The rules already fix the shape: uploads go through the API and nowhere else, sharp re-encodes them, three WebP variants are made under content-addressed keys, the original is discarded, and photos are served as signed CloudFront URLs with a fifteen-minute TTL whose issuance is logged per account. What this ADR records is how those pieces fit together in infrastructure and code, and the decisions the rules leave open: where the distribution sits, how the signing key is held, what a developer's machine does instead, and how the switch from "TLS at Traefik on the box" to "TLS at CloudFront" happens.

## Decision

1. **One distribution per environment, on the API's own name.** `api.<env>.kuutti.app` becomes a CloudFront alias. The default behaviour is the API on the box (nothing cached, every viewer header forwarded, so Traefik routes by Host and the API keeps seeing its public name); the behaviour `/media/*` is the private media bucket, read through origin access control, and served only with a URL the API signed. The API never registers a route under `/media/`. A second host for media was considered and rejected: one certificate, one alias, one place for CORS and headers, and the rate limiter's view of the client does not change between photos and JSON. TLS to viewers terminates at CloudFront with an ACM certificate from us-east-1; the hop to the box is HTTPS to `origin.api.<env>.kuutti.app`, whose Let's Encrypt certificate Traefik obtains as it does today (the name points at the Elastic IP, so the HTTP-01 challenge still reaches the box).
2. **Content-addressed, three variants, no original.** The key is the SHA-256 of the re-encoded `full` variant; objects live at `media/<key>/{thumb,card,full}.webp` with an immutable cache header. The same picture uploaded twice, by one person or two, is one set of objects and two rows; the row is the account's, the objects go when the last row does. The pixel cap is applied to the file header before a decoder runs, the size cap to the request before a byte of the body is read, and above the concurrency limit the upload answers 503 with `Retry-After` rather than queueing.
3. **Canned-policy signed URLs, fifteen minutes, one object.** The API signs `https://api.<env>.kuutti.app/media/<key>/<variant>.webp` with RSA-SHA256 over the canned policy. The public half of the key pair is a CloudFront public key in a key group the media behaviour trusts, declared in code from a committed PEM; the private half is `/kuutti/<env>/cloudfront-signing-key` in SSM, read at boot through the instance role, never a resource (ADR-001), with a custody row. Signed cookies were rejected: a cookie grants a path prefix to a browser session, and there is no browser (rule 8). Rotation is a second public key in the group, a new SSM value, a restart, then the removal of the old key.
4. **Only one's own photos are served in M3.** The URL route's query is scoped by the caller's account; another person's photos arrive with the profile card (#47) under the shown-record rule of the exposure budget (#52), never before. Every issuance is a `photo_access` row and a log line with account, photo, variant and time; the budget counts from that table.
5. **Locally, the S3 stand-in presigns its own GETs.** A developer's machine has no CloudFront; the API's `UrlSigner` seam has a second implementation that presigns a GET on the compose stand-in (versitygw) for the same fifteen minutes. It is refused outside `APP_ENV=development|test` at boot, so no deployed environment can fall back to it. A half-configured CloudFront (a base URL without a key, or a key without an id) also fails the boot, as a half-configured OIDC does. A pull-request preview has no media at all: it reads staging's parameter prefix, and the configuration drops the bucket's URL base and the signing key for `APP_ENV=preview` the way it drops the application database password, so a preview can neither sign staging URLs nor delete staging's objects (their reference counts live in staging's database, not in `kuutti_pr_<n>`); its photo routes answer 503.
6. **The cutover is a commit, after three manual steps.** The module is wired behind `media_enabled` (default `false`) in both environments so this decision can merge without a key pair that does not exist yet. The maintainer generates the RSA-2048 pair offline, puts the private half in SSM, commits the public half as `infra/envs/<env>/cloudfront-signing-key.pub.pem`, gives the `api` application in Dokploy the `origin.api.<env>` domain, and sets `media_enabled = true`. The apply then creates the bucket, the certificate, the distribution, moves `api.<env>` from the Elastic IP to the alias, points `origin.api.<env>` at the box, attaches the bucket policy to the instance role and writes `s3-bucket`, `media-url-base` and `cloudfront-key-pair-id` under `/kuutti/<env>/`. The next deploy boots with media on.
7. **CloudFront-only ingress is a second switch, off for now.** `cloudfront_only_ingress` replaces the world-open 443 rule with CloudFront's origin-facing prefix list (audit F141). It stays off because two other things are served on the same port directly: Dokploy's control plane, which `deploy.yml` calls, and the pull-request previews on `*.preview.api.<env>`. Putting them behind the distribution (aliases, a wildcard on the certificate, Host forwarding is already there) is the follow-up that lets the switch flip; until then the security checklist's ingress lines stay open, and say so.

## Consequences

- The API image carries sharp's native addon and libvips for linux-arm64 outside the bundle (`tsup` externals; the platform's two packages and `@img/colour`, three directories copied in the Dockerfile, #416); sharp is imported at module level, so a missing or wrong binary fails the boot and the image smoke test, not the first upload. libvips is LGPL-2.1-or-later, used under LGPL-3.0: server-side, dynamically loaded, built by sharp-libvips with its patches (#416), listed as an exception in `scripts/license-policy.json` with that reason.
- Rate limiting by client address behind CloudFront needs the viewer address from CloudFront's own header rather than the first `X-Forwarded-For` hop, and the request id must stop being client-settable (audit F19, F26). Both are #52's, and both become live the day `media_enabled` is set; #52 lands before or with the cutover.
- Photos of other people are not reachable at all in M3, even approved ones. The profile card issue widens the visibility rule; nothing here has to be undone.
- The on-device nudity check runs before upload behind an interface with a pass-through implementation; the model is a native change for the October batch (#48). Rekognition (#49) remains the authority.
- Deleting a photo deletes its objects only when no other row shares the key; a person who uploaded the same picture twice and deletes one copy keeps the other, as expected.

## Alternatives considered

**Resizing at the edge (Lambda@Edge or an image CDN).** Rejected: not adopted by `.claude/rules/infra.md` (no Lambda for images), and moderation needs the variants at upload time, not on first view.

**Presigned S3 GET URLs in production.** Rejected: they bypass CloudFront's cache and TLS at the edge, expose the bucket's host, and S3's signature gives no key-group indirection for rotation.

**A separate `media.<env>` host.** Rejected as above: nothing gained for a second certificate and alias, and the anti-scraping work wants one ingress.

**Keeping the original for re-processing.** Rejected by rule 4 and TD-8: nothing needs it, and a breach of originals is the worst case.

## History

- 2026-10-09: staging cut over with `media_enabled` alone (`infra/envs/staging`): the key pair of §3 created, its public half committed, the `origin.api.staging` domain given to the `api` application. The ingress switch of §7 stays off, so until Dokploy and the previews are behind the distribution the rate limiter keys on the CloudFront edge that forwarded the request (ADR-008 §5 and History, `infra/README.md` Media): one sender near an edge can exhaust the anonymous buckets for every phone behind it for the window. The maintainer accepts that for staging, where those phones are the team's; production keeps the order of §7.
- 2026-10-18 (#350, ADR-031 §10): a second purpose. A photo sent in a conversation goes through the same pipeline, as a row of `photo` with `purpose = message` and no position (migration 0056), checked before anything is stored (ADR-006), its row and its message one transaction. Its thumb and full size are signed for the conversation's two people only, in a page of the conversation, the read of one message and the send's answer to its sender (201, and 200 for a resend), never in a socket frame. The URLs end at the next five-minute mark plus fifteen minutes, so they live 15 to 20 minutes rather than §3's fifteen, and on CloudFront a repeated read inside the five minutes gets the same URL (the stand-in of §5 presigns afresh). The fetch log has one row per viewer, photo and variant in each five-minute window, with the purpose `message` and never counted (ADR-008); two reads at the same instant, in two transactions, may each write theirs. The profile's reads ask for `profile`: a message photo is never on a card, a photos screen, the moderators' queue or a conversation's thumb, and the photo routes answer 404 for it.
- 2026-10-22 (#416): the image carries the notices of what it carries. The API's build writes `dist/THIRD_PARTY_NOTICES` after tsup (`apps/api/scripts/notices.ts`): every package esbuild's metafile names (the source maps cannot say, since esbuild composes them with the packages' own) and the packages of `node_modules/@img`, which are three, not the two this record named (`@img/colour` too), each with its copyright lines, licence texts and NOTICE files as `@kuutti/notices` reads them; the twelve bundled packages that ship no licence file take rows of a table kept in `scripts/notices/third-party.ts`, with the upstream address of each. libvips is a part of its own (`apps/api/notices/libvips.json`, gathered by hand on 22/10/2026 from sharp-libvips 1.3.4 and from each library at the version it names): the prominent notice LGPL-3.0 4(a) asks for; the texts of LGPL-3.0 and of GPL-3.0, whose terms it adds its permissions to, since every library under the LGPL is used under its version 3 (sharp-libvips' own reading, through each one's "or later"); each of the 28 libraries, Rust's standard library and the 126 Rust crates built into it (122 of librsvg's own, four of the standard library's) with the licence it is used under, its copyright lines and texts, the credit statements FreeType's and the IJG's licences ask for, and the release and patches it is built from; `apps/api/notices/README.md` says how to gather it again. Those are GPL-3.0 6(d)'s directions to the Corresponding Source, on sharp-libvips' servers and each library's, and 6(d) leaves the image's publisher obliged to keep that source reachable while the image is offered: whether Kuutti keeps a copy of its own is the maintainer's open point. `/app/LICENSE` and `/app/LICENSE-EXCEPTION` go into the image as well. A bundled package with no text, or a libvips other than the one gathered, fails the build, in the Dockerfile too, and `build.yml` checks that the image it built carries both files.
