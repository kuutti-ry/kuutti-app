# ADR-051: The moderation panel's flows in a browser, with Playwright

- Status: proposed (built as written here; when CI runs it, §8, is the maintainer's to settle, and so is accepting it)
- Date: 2026-10-24
- Follows: TD-2 (the stack: its test runners), TD-17 (the panel is English), ADR-020 (end-to-end flows; its "left for later: the admin panel with Playwright"), ADR-025 §3 (the panel's content security policy), ADR-050 §6 (the CSP checked by hand in a browser), ADR-006 §5 (staff roles granted with the maintainer's command line), ADR-014 (the personas live at the mock bank), ADR-021 (tests at every level), CLAUDE.md (a new dependency; testing); issue #106

## Context

The panel had jsdom tests only: Vitest and Testing Library with `fetch` stubbed, and a test of its build. Nothing drove a browser against the real API, the mock bank or the host's CSP. The CSP is what decides most of the panel's design (ADR-050), and it was checked by hand: the production build served with the policy of `infra/modules/admin/main.tf`, a sign-in through the mock bank, every screen opened, the console read (ADR-050 §6, 24/10/2026). A jsdom test cannot see that a browser refuses a `<style>`, that the bank's redirect lands on the panel with a code, that the API answers the panel's origin, or that a photo's signed URL loads under `img-src`.

ADR-020 drives the phone app with Maestro and left the panel for later. Maestro drives phones; a web page is Playwright's ground.

## Decision

1. **Playwright Test, Chromium only,** a development dependency of the panel (`@playwright/test` 1.64.1, pinned; Apache-2.0, three packages, none with an install script). The browser is not a package: `playwright install chromium` fetches Playwright's build of it from Playwright's download host, once on a laptop (in `apps/admin`, `npx playwright install chromium`), and in CI as a step of its own with the headless shell alone and the runner's system libraries (`--with-deps --only-shell`), cached by the version. Staff use the panel in a desktop browser; Firefox and WebKit would add two downloads and run time for nothing the CSP or the flows tell apart.
2. **The real stack, with a database and a bucket of its own.** `pnpm e2e:admin` (`apps/admin/e2e/run.ts`) needs docker compose's Postgres, mock bank and S3 stand-in and the release of pictures, and nothing else of the local environment. It makes `kuutti_test_admin_e2e` and the stand-in's bucket `kuutti-test-admin-e2e` anew, migrates and seeds the database, starts the API from source against both on a free port, configured from `env.example` and never from `.env` (rule 9), builds the panel for production against that API and serves the build on another free port. Other sessions share the local stack (Postgres, the bank, the stand-in and often an API on 3000): the run writes nothing the shared stack holds, refuses any database not named `kuutti_test_…` and any database server or object store on another computer, and needs nobody's API. The bucket is its own because a photo's objects are named by their content: the cast's pictures have the same names in every database, so an erasure on either side, judging by its own rows alone, would take the other's (a first version of this run, cleaning up through the erasure path in the shared bucket, emptied the shared stack's photos on 24/10/2026). One run at a time on a machine: the run holds an advisory lock on the database server from its first step to its last, and a second run stops at once, said so. Afterwards, whatever the flows did and a signal included, it stops what it started, empties and removes the bucket and drops the database; a run killed outright leaves both to the next run, which makes them anew.
3. **The host's headers, read from the module.** The panel's server answers every path that is not a file with `index.html` (the distribution's 403 and 404, #302) and every answer with the headers of the module's response-headers policy, parsed from `main.tf` rather than copied, the API's origin standing for `var.api_origin`. One addition, and only locally: the S3 stand-in's origin in `img-src`, since the local API presigns photo URLs on the stand-in, where a deployed one serves them from its own origin through CloudFront. A policy the reading cannot follow (another variable, no `img-src`) stops the run rather than loosen it; `run.ts --self-test`, in CI's `lint` job, holds the reading to the shipped module.
4. **A clean console is part of every flow.** A fixture fails a flow on any console error or warning, uncaught error, or `securitypolicyviolation` event on the panel's origin; the mock bank's page is not the panel's. One flow writes a `<style>` on purpose and expects the guard to see the refusal, as the event and in the console, so the guard and the policy are shown to be on.
5. **The data comes the product's own ways.** The cast's stories (`demo:reset`, through the API's routes) leave Noa's photos waiting for a person (locally every upload does, `MODERATION=queue`). Mikael signs in once, as anybody does, and gets the moderator role from the maintainer's command line, granted to the identity that signed in last (`moderator recent`, then `grant`, ADR-006 §5). Laura reports her conversation with Emmi through the app's route, and Iida's round names Riikka, whose page the sanction flow opens. No route, no SQL and no seed exist for the flows.
6. **Few flows, each a moderator's whole task, in any order:** sign in at the bank and see what waits, with the return to the screen asked for and a bank login without a role refused; the photo queue, one approved and one rejected for a reason chosen on purpose, the picture loaded through its signed URL and the count going down; a report read, with its frozen conversation, and dismissed through its confirm step; a person's page found by account id, a suspension applied and lifted, each through its confirm step; the keyboard on a confirm step (the focus inside, Tab and Shift+Tab wrapping, the page inert, Escape, the focus returned); and an admin's screen refused to a moderator without a request. One worker, since the flows share one database; no flow relies on another having run, and none can run twice on one stack (a retry finds its photos decided and its report dismissed), so a flaky flow is fixed, never retried. The flows match the panel's English texts of `messages.yaml` (TD-17), so a changed text breaks a flow, which is the point, as in ADR-020 §5.
7. **What the jsdom tests keep.** Every branch, refusal and error of a screen stays a Vitest test, with its coverage floor (ADR-021); a flow proves the parts hold together in a browser under the host's policy, not the branches again.
8. **CI: `.github/workflows/e2e-admin.yml`,** on every push to `main`, on a pull request that changes what the flows exercise (the panel, the API, the packages, the mock bank, the panel's host module, the stack's files; each push), and by hand. No environment, no secret, `contents: read`, not a required check. Its first run, on #443 with Chromium not yet cached, took 1 minute 42 seconds: 22 seconds to start the stack, 14 for Chromium and its libraries, 27 for the run (the eleven flows 10 of them), the rest the checkout and the install; on a laptop the run is about half a minute. Unlike ADR-020 §6's hour, this is cheap enough not to wait for a label; whether it should wait for one anyway, and whether it becomes a required check, are the maintainer's.

## Consequences

- `pnpm e2e:admin` (and `pnpm --filter @kuutti/admin e2e`), `apps/admin/e2e/README.md`, a line in CLAUDE.md's commands and in `.claude/rules/admin.md`; the panel's typecheck covers `e2e/` with a project of its own. For the run's bucket the panel lists `@aws-sdk/client-s3` as a development dependency, the API's own version, already installed. `apps/admin/e2e/.out` (the build, the logs, Playwright's results) is ignored by git.
- ADR-050 §6's check by hand now runs on every change of the panel.
- The flows read the module's file: a change of the panel's headers in `infra/modules/admin/main.tf` is a change of what the flows run under, so the workflow runs on it.
- Left out, each with what would bring it: the admin's own flows (a tunable changed, a ban, the second look, the automatic bans), which need a second member of staff and an admin persona, and come with a change to one of those screens; Firefox and WebKit, if staff use them; a phone-sized window, if staff moderate from a phone; an accessibility scan (axe-core, a new dependency) beside the keyboard flow; screenshots compared from run to run; a flow across both apps (the moderator's decision on Noa's photos seen in the app, ADR-020's list); the flows against a preview on staging, which has Telia's bed and no mock bank.

## Open, the maintainer's

- §8: on every pull request that touches what the flows exercise, as built, or only with the label `e2e`, as the Maestro flows; and whether `e2e-admin` joins the required checks once it has proved steady.
