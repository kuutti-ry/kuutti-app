# ADR-012: Preview cleanup runs unattended from main

- Status: accepted, amended 2026-10-08 (the reviewer on `preview` that §1, §2, §7 and §9 name is off from that day, ADR-004 §3; the points stand on the sweep running `main`'s copy, on its `actions: write` job and the plan role trusting `main` alone, and on the environment's branch policy, not on the reviewer)
- Date: 2026-09-27
- Follows: TD-2 (free tiers, three previews), TD-19 (one staging box, previews on it), ADR-004 §3 (the trust of the `preview` environment: a reviewer from 2026-09-25 to 2026-10-08, write access from then), `.github/scripts/check-workflow-permissions.py` (no `pull_request_target`), CLAUDE.md "Do not add infrastructure for scale that is not coming"; issue #9, the staging outage of 2026-09-27

## Context

`preview-cleanup.yml` removed a pull request's previews on its `closed` event and in a nightly sweep, both under the `preview` environment, whose required reviewer is the maintainer. The reviewer is right for deploys: `preview.yml` runs a pull request's own code and its own copy of the workflow with the Dokploy and Expo tokens, so someone must look first (ADR-004). For removals it meant that every close and every nightly sweep waited for a click that did not come. On 2026-09-27 the staging box, a t4g.small with 1.8 GB and no swap, carried the previews of three merged pull requests (#64, #66, #69) next to the staging API and Dokploy, which itself takes 0.8 to 1 GB; the kernel's OOM killer took Dokploy every two minutes, each kill broke the Swarm agent's heartbeat, the manager restarted every service, and the API was unreachable for about an hour. The previews were removed by hand.

## Decision

1. **Cleanup never waits for a person.** It runs from `main` only: a sweep every ten minutes that removes the previews of every closed or merged pull request and retires previews older than seven days, and a `workflow_dispatch` for one pull request number or a sweep. The `pull_request: closed` trigger is gone: that event runs the pull request's copy of the workflow, which would hand a contributor the tokens without a reviewer. `pull_request_target` would run main's copy but is banned in this repository, and the ban stands. Ten minutes after a merge is close enough to "on merge" for a box that must never again hold the previews of merged work.
2. **Its own environment, `preview-cleanup`, without a reviewer.** It holds the same two secrets as `preview` (`DOKPLOY_TOKEN`, `EXPO_TOKEN`) and the same variables (`DOKPLOY_URL`, `DOKPLOY_ENVIRONMENT_ID`, `PREVIEW_API_DOMAIN`, `EAS_HOSTING_SUBDOMAIN`). Nothing in the job runs code from a pull request, so nothing needs a reviewer; the tokens stay out of the repository level as before. The `preview` environment keeps its reviewer for deploys.
3. **The database job is unchanged.** It has no environment and exchanges the run's OIDC token for the plan role, which trusts `main`; a scheduled or dispatched run on `main` presents that subject.
4. **Order, and what may block what.** Select, drop the database, remove the EAS alias and branch, remove the Dokploy application. The application is the sweep's work list, so it goes only after its database: a failed drop is retried by the next sweep. A failure at EAS never keeps a container on the box: the application is removed regardless, and the run then fails naming the alias or branch that is left, for a removal by hand. A leftover alias at Expo costs nothing; a leftover container costs the box.
5. **An empty sweep costs seconds.** The selection step needs only `gh`, `curl` and `jq`, which the runner has; pnpm and the EAS CLI are set up only when there is something to remove.
6. **The merge itself starts the sweep** (amended 2026-09-27, the same day). Point 1 counted on the schedule, and the schedule did not come: GitHub starts scheduled workflows when it has room, and in this repository a `*/5` and a `*/10` cron both ran once in two to six hours; after this workflow reached `main` no scheduled run of it started for two hours. So the sweep also runs on every `push` to `main`. A merge is a push to `main`, the event runs `main`'s copy of the file, never a pull request's, and the run presents the same OIDC subject as a scheduled one. The schedule stays for what no merge follows: a pull request closed unmerged, and the seven days. Those may wait hours; a merged pull request's preview does not.
7. **A preview run that outlives its pull request deploys nothing** (the same amendment). A run of `preview.yml` waits: for the image, for the reviewer of the `preview` environment, for the lane before it. Merged in the meantime, it would put back what the sweep removed, and an alias made at EAS after the application is gone is one no sweep finds. So every lane asks whether the pull request is still open right before it deploys (`.github/scripts/pr-open.sh`) and does nothing when it is not; a state that cannot be read fails the lane. What is left is a merge in the seconds between the question and the deployment: the application then exists when the merge's sweep lists it, or is found by the next one.

8. **A run that waits for a pull request that is not open is withdrawn** (amended 2026-09-28; the maintainer allowed the permission for this one job, and confirmed it against what it is, below). Point 7 made such a run harmless; it did not make it go away. A run of `preview.yml` that nobody approved stays "waiting for review" for the thirty days GitHub gives it, and after five merges the maintainer's list of deployments to review held five of merged work beside the one that was real. The sweep never saw them: its work list is what is on the box, and a run that was not approved put nothing there. One of the five was started before point 7 existed, by the workflow file as it then was, and would have deployed on a click (the next sweep would have removed it). So the sweep has a second job, `waiting`, beside the three that remove: it lists the runs of `preview.yml` that a pull request started and that wait, asks for the pull requests of each run's branch, and cancels the run when a closed one is found and no open one (`.github/scripts/withdraw-waiting-runs.sh`). By the branch, because GitHub empties a run's own list of pull requests when the pull request closes; by the branch of its owner, never by the name alone, because anybody can open and close pull requests from a fork's branch of the same name. A run therefore stays while any pull request of its branch is open, a later one on a reused branch included. Whatever cannot be read is left waiting, with a warning: a run withdrawn by mistake costs somebody a push, a run left costs nothing.

   **What the permission is.** The job has `actions: write`, and it uses it to cancel. The scope is wider than its use: with it a token can also re-run and delete runs and their logs, start any workflow that has a `workflow_dispatch` trigger, disable and enable workflows, approve the runs of pull requests from forks, delete caches and artifacts, and set the template of the repository's OIDC subject claim. (That last one by GitHub's REST documentation, read 2026-09-28, which names `Actions` write for the repository's template and `Administration` for the organisation's; whether a run's own token is accepted there was not tried. The AWS roles match on the repository's and the owner's id, not on the subject: `.claude/rules/infra.md`.) What keeps the scope to its use is where the job runs and what it runs: `main`'s copy of one script, in a job that takes no environment and so holds no secret, in a workflow no pull request starts. The invariants script holds the job to its whole shape (its condition, its runner and the workflow's shell to the letter, a checkout of the scripts, the one script, the run's own token; a step, a key or a value more or other fails CI) and holds that no other job has the scope. What the script itself does is held by its test and by the review of a change to it, as for any code on `main`. It is a check in CI, not a lock: somebody with write access can give a workflow on a branch of their own any scope the repository allows, with or without this job; what they cannot get that way is a secret, which is point 9.

   The other way, a `closed` trigger on `preview.yml` whose run would cancel the waiting one through the concurrency group, needs no permission and was not taken: it runs the pull request's copy of the file, so a pull request that predates it or edits it is not covered, and it does nothing for the runs that wait already.
9. **The environment `preview-cleanup` takes deployments from `main` only** (amended 2026-09-28; a setting, made by the maintainer). Point 2 gave the cleanup an environment without a reviewer, because nothing in the sweep runs a pull request's code. That is true of the workflow on `main` and of nothing else: an environment is asked for by name, and a workflow file on any branch may name it. With no branch policy, anybody with write access could push a branch whose workflow names `preview-cleanup` and be handed the Dokploy and the Expo token without a review, which is what the reviewer on `preview` exists to prevent (ADR-004 §3). The condition `github.ref == 'refs/heads/main'` in the workflow does not help: on a branch the file is the branch's. So the environment has a deployment branch policy of `main`, as `staging` has: the maintainer set it on 2026-09-28, it was read back through the API, and a sweep dispatched from `main` passed the environment after it. The sweep is not touched by it: a push to `main`, the schedule and a dispatch from `main` all run on `main`. Found by the security review of point 8; the environment had been without the policy since it was made, on 2026-09-27.

## Consequences

- The maintainer creates the `preview-cleanup` environment once and sets its two secrets (`gh secret set DOKPLOY_TOKEN --env preview-cleanup`, the same for `EXPO_TOKEN`); the variables are copied by API. Until the secrets exist the sweep fails at its first Dokploy call and removes nothing.
- The sticky comment on a merged pull request ("Previews removed") now comes from the sweep its merge started, a minute or two after it; on a pull request closed unmerged, from the next sweep, whenever a push or the schedule starts one.
- A preview run that waits when its pull request merges is cancelled by the sweep that merge starts, and shows as cancelled in the list of runs; one whose pull request closes unmerged, by the next sweep. What is left in the maintainer's list of deployments to review is of branches that have an open pull request, and whatever the sweep left because it could not tell: a run that names no branch or no repository, a branch no pull request is found for, a question GitHub did not answer. Each of those is a warning in the sweep's log, by the run's number.
- The branch policy of point 9 is part of the environment's setup (`infra/README.md`, Previews, step 6). The tokens the environment held while it had none, from 2026-09-27 to 2026-09-28, were within reach of anybody who had write access in that time: the owners and the four contributors. Nothing says that anybody reached for them, and nothing in the repository could say so. The maintainer decided on 2026-09-28 not to rotate them.
- Open, for the box itself (the same outage): swap on the instance and a memory limit on Dokploy's service, so one process growing cannot take the API with it; tracked separately.
