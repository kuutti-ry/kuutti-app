# ADR-026: Limits per person, and the sign-in doors

- Status: accepted (the numbers of §5 are the maintainer's to change, in the parameter store), amended 2026-10-16 (§6, §8: a callback spends its attempt, #324) and 2026-10-17 (§8: a staff attempt's refusal at the claim goes back to the panel, #250); see History
- Date: 2026-10-16
- Follows: TD-3 (one box, in-process limits, no Redis), TD-6 (abuse and scraping), ADR-008 §5 (whose word the API takes for a client's address), CLAUDE.md "Security and privacy defaults" (logs carry no personal data), the security checklist ("rate-limited endpoints fail closed"); issues #41, #35, #52

## Context

The API has one limiter: a fixed window of `RATE_LIMIT_PER_MINUTE` requests per client address (ADR-008 §5), in memory, failing closed. Finnish mobile networks put many people behind one address (CGNAT), so a per-address limit both lets an attacker with many addresses through and stops real people who share one. The bank login gives the API something better once a person is signed in: a session is one real Finnish adult, and a ban binds the identity (ADR-024). Before the login it gives nothing, and those doors are the cheap ones to flood: every `GET /auth/start` writes an `auth_request` row and signs a request object for Telia, and the table had no bound but the nightly sweep of expired rows.

Reading the code for #41 also showed that three media routes run the session guard twice (overlapping route patterns), that the request log line carries no staff identity, and that an IPv6 client can change its address within its /64 at will, while one subscriber is usually given a /56, 256 of them (RIPE-690).

## Decision

1. **Two keys, one mechanism.** The limiter stays a fixed window in memory (TD-3); what changes is the key. Before a guard knows who is asking, a request is counted by its client address as ADR-008 §5 reads it, with an IPv6 address counted by its /64 and an IPv4-mapped IPv6 address as the IPv4 it maps. The sign-in doors of point 4 count an IPv6 address by its /56 instead: counted by /64, one subscriber's delegation would be 256 windows at the doors, enough to fill the table of point 6 alone. The address's own limit keeps the /64, since it counts everything a device does before a guard admits it, and the several devices of one home should not share it. A request a guard admits is counted again by its person: the account for the app's routes, the staff identity for the panel's.

2. **A person's request leaves the address's count.** The address is charged first, since nothing else is known then; once a guard has admitted the request and the person's limiter has counted it, the charge is given back to the address within the same window. The give-back follows the person's count, not the guard: a guard that ever runs without the person's limiter leaves its requests on the address, never unlimited. So two people behind one address do not spend each other's budget, and a stream of requests with no valid session still meets the address limit. A token that opens no session (missing, malformed, unknown, revoked, expired) stays charged to the address. A live session that floods past its own budget costs one indexed session lookup per refused request; it belongs to a known person, who can be banned. The routes that end a session or the account, `POST /auth/logout`, `/auth/logout-all`, `/admin/auth/logout`, `/account/delete` and `/account/pause` (`ENDS_SESSION` in `app.ts`), are outside the person's budget and are not given back to the address. The person's budget is the account's, shared by every session of it, so somebody holding one stolen session could otherwise spend it every window and keep the owner from signing every device out, pausing or deleting from any other device; those routes stay bounded by the address's limit instead.

3. **Counted once per request.** One limiter counts a request once even when two guards run on it, so the media routes whose patterns overlap are not charged twice. The person's limiter is one instance across the app's guard and the three staff guards, so a member of staff has one budget, not one per role check.

4. **The sign-in doors have a window of their own.** The doors are the two starts, `GET /auth/start` and `GET /admin/auth/start`: each writes an `auth_request` row and has the broker sign a request object, so they are the cheap ones to flood. They share a window per address, an IPv6 client counted by its /56 (point 1), applied before anything is written or signed: a refused start never reaches the table or the broker. The exchanges are no doors. A person who exchanges a code has been through the bank, which the association pays for, and a window counted on starts must not refuse them at the last step; an exchange that is nobody's costs a hash and an indexed lookup. They stay under the address's limit of point 1 with `/auth/callback` and `/auth/refresh`, and its refusal is their 429 `rate_limited`. A refused start redirects as every other sign-in refusal does, to the app's link or the panel's page with `error=auth_rate_limited` and `Retry-After`, so a person in the system browser is not left on a JSON page. The address's limit sends a start it refuses back the same way, since it runs first and on a preview its 30 a minute is tighter than the doors' 60; every other path it refuses answers 429 `rate_limited`.

5. **The numbers are configuration, not product rules.** `RATE_LIMIT_PER_MINUTE` (SSM `rate-limit-per-minute`) is both the address's and the person's budget: 120 a minute, 30 on a preview. `SIGN_IN_RATE_LIMIT_PER_MINUTE` (SSM `sign-in-rate-limit-per-minute`) is the doors': 10 a minute in production, 60 elsewhere, since staging keys on the CloudFront edge until its ingress switch (ADR-008 History) and the demo's reset signs many personas in from one address. They are security settings, read at boot, so a change applies at the next restart without a deploy; `matching_config` would add a query to every request.

6. **`auth_request` has a ceiling, and a full table refuses nobody.** A start inserts its row only while the table holds fewer than 50,000 rows, counted in the insert's own statement: a guard for the disk, some twelve megabytes with the indexes, far above real use (a couple of hundred attempts in a launch hour). At the ceiling the expired rows are deleted first, and the table is counted again only if that freed something. If the table is still full, the two oldest attempts the bank has not answered yet, those without a code whose callback has not come back, are deleted and the new attempt is inserted in their place, in one statement with no count, so no other start can take the room in between. A flood thus shortens how long an unanswered attempt lives instead of shutting the door: refusing at the ceiling would make the table one switch for every sign-in in the country, the panel's included, that one routed prefix could hold down. An attempt that holds a code, or whose callback is under way (§8), is never deleted: its person has been to the bank. Only a table whose every row holds a code or a callback under way refuses a start, as point 4 does, with the doors' window as the wait; nobody keeps such a row without a bank identification, since a callback the bank does not complete ends its attempt at once (§8), so at this size it does not happen, and the refusal stays only so that the table fails closed. Concurrent starts can overshoot the ceiling by at most the connection pool's size; a start at the ceiling ends two attempts and adds one, so the excess drains, a row a start, and a table under a flood sits near the ceiling: up to about as many rows under it as starts are in flight, and at most the connection pool's size over it. Two starts evicting at once skip each other's rows rather than wait. The nightly sweep stays.

7. **Nothing stores or logs an address.** The keys live in memory for at most two windows (expired buckets are dropped once per window, not only past a size), and no log line, error or answer carries one. The PII-in-logs test sends addresses through every route in every trusted-proxy mode, IPv4 and IPv6, and through every refusal, and fails on any line that carries one. `check-schema-words` refuses a column named for an address, the address words also as a segment of a snake_case name (`ip_hash`, `last_ip`). The request log line carries the staff identity for the panel's requests, as it carries the account for the app's. A start refused by the doors, the address's limit or the ceiling answers 302, so the request line does not show it as a 429; it leaves a warn line instead, `msg: "sign-in refused"` with `code: "auth_rate_limited"` and `detail.limiter` `address` or `cap`. An eviction at the ceiling leaves the same `msg` with `detail.limiter: "evicted"` and `detail.evicted`, how many attempts it ended. These lines are the signal the runbook and the alarm of the infra half of #41 watch for sign-in floods, a metric filter on `{ $.msg = "sign-in refused" }` with `evicted` as the sign that the table is full; every other refusal of the limits is a 429 on the request line.

8. **A callback spends its attempt** (#324). The callback's first statement claims the attempt by its state, before the broker is asked anything: one `UPDATE ... RETURNING` that takes the row only while it has no code, no claim and time left, sets `outcome` to `answered` and moves `expires_at` to ten minutes from the callback (`AUTH_REQUEST_TTL_MS`). A state it does not take, unknown, answered already, holding a code or expired, answers `auth_state_mismatch` with no token call at Telia; two returns at once are one claim and one refusal, since the second waits on the row's lock and then reads the mark. The eviction of §6 skips a claimed row and the sweep of expired rows does not reach it before its deadline, so no attempt is ended while its callback is under way. The deadline is a bound for a crash, not a wait: the broker's client gives up on a request after 30 seconds. A callback that ends in a refusal or a failure, any `AppError` (the broker's error or an error answer, a cancel, an authentication that predates the attempt, a minor, a refused identity, staff without a role), expires its attempt there and then: the mark keeps refusing a replay, and the row is the sweep's, the first thing a start at the ceiling clears, rather than one the eviction must skip for ten minutes, which one start and one bogus callback could otherwise leave and enough of them would turn into a table that refuses every start. A 500 keeps its claim until the deadline, so its own error reaches the error sink unmasked; a process that dies mid-callback leaves its row for ten minutes at most. A state the claim does not take still names its row, so the refusal reads the attempt's platform by the state and sends a staff attempt's browser back to the panel, the app's to the app's link (#250); only a state no row holds, never written, evicted or swept, lands on the app's link whatever it was, since nothing says otherwise. The read is one more lookup by the unique state, on a refusal only, and tells nobody more than the state they hold, which a successful callback shows anyway. The app's text for `auth_state_mismatch` already says to start again and the panel's generic one says to try again, so no code or text is new. `outcome` carries the mark, so no migration: NULL while the attempt waits on the bank, `answered` once claimed (and on an attempt spent without a code), then `created`, `resumed`, `unpaused` or `admin` from the attach; the exchange finds its row by the code's hash and never reads `answered`. A refused identity is counted once per bank login, where a replay used to count it again.

## Consequences

- An anonymous flood from one address still refuses everyone behind it for the rest of the window, signed in or not: the address is counted before a guard knows who is asking (§2), so a spent address refuses a session's request before the guard can give the count back. Point 2 keeps people behind one address from spending each other's budget; it does not shield them from a flood that spends the address. The edge rule of #41 (AWS WAF, the maintainer's half, with the alarms) is what stops volume before the box.
- A flood of starts from many addresses no longer refuses anybody's start. One key at the doors, an IPv4 address or an IPv6 /56, holds about 110 unexpired rows (ten a minute for the ten minutes an attempt lives, plus the fixed window's edge), so some 450 keys keep the table at its ceiling. What that does to everybody is end the unanswered attempts sooner: to push out the attempt of a person at the bank, a flood must start 50,000 more within that person's minute or two there, 2,500 to 5,000 keys at ten a minute each. A person whose attempt was ended comes back to `auth_state_mismatch`, which the app says as an attempt unknown or expired, and starts again: an attempt ended before its callback leaves a state the callback does not know. An attempt whose callback has come back is never ended (§8), so a login under way completes however full the table is. A staff attempt ended before its callback lands on the app's link rather than the panel's, as any unknown state does. Staff already signed in keep their eight-hour sessions throughout.
- A start at the ceiling costs one counted insert, whose count over 50,000 rows takes a few milliseconds, as every start's does on a table the flood keeps full, plus one statement that walks the expiry index to the two oldest unanswered attempts and deletes them by primary key, a fraction of a millisecond. The sweep of expired rows adds a second count only when it freed something. Holding the table at its ceiling takes some eighty starts a second, a real share of the database's two burstable cores: the edge rule of #41 is what keeps such a flood off the box.
- One client behind a shared IPv4 address, or within one IPv6 /56, can keep everybody else there from starting a sign-in for the rest of the window by sending more starts than the doors allow. That is the price of the /56 key and of CGNAT: mobile networks may give each phone its own /64 out of one /56, so a /56 can be many unrelated people. Counting the doors per /64, with a wider budget per /56 beside it, would narrow this at the cost of a second bucket.
- Anyone holding a state, which travels in the browser's address to Telia and back, can spend it with one bogus callback, and the person's own return then meets `auth_state_mismatch` and starts again (§8). That costs the person one login; before §8 the same holder could replay the callback for the attempt's ten minutes, a token call at Telia each time.
- A stolen session can send the routes of §2 that end a session past the person's budget, bounded by each address it has; each either ends that session or the account's, which the session could do once anyway, or is refused before it changes anything (no confirmation, an account not in the state the route needs) and counts on the address's window like a request whose token opens no session.
- Resets of the demo in quick succession wait for the doors' window from about the eighth in one minute: a reset spends some eight starts of development's sixty, its exchanges none. The demo's client already waits as long as `Retry-After` asks.
- Upload, like and message budgets are not here: no like or message route exists yet, and uploads are bounded by `max_photos`, the size cap and the upload pool. They come with their routes, as product tunables in `matching_config`.

## Alternatives considered

- **Redis or a shared store:** one box (TD-3).
- **The numbers in `matching_config`:** a query on every request for a security setting no product decision moves.
- **A start that writes nothing until the callback** (the state signed instead of stored): the root fix for the table's growth, but it changes the Telia flow; its own issue and ADR if the ceiling ever bites.
- **A separate address bucket charged only after a failed token:** more state for the same bound as point 2.
- **Hashed keys:** memory is not storage; the keys live for two windows and reach no log.
- **The exchanges as doors** (the first version of point 4): it refused people after the bank, and halved the starts a shared address gets.
- **Refusing every start at the ceiling** (the first version of point 6): one switch for everybody's sign-in, which one IPv6 subscriber could hold down with the doors counting /64s.
- **Keeping staff attempts out of the eviction, or a share reserved for them:** an evicted staff attempt costs a second click, and the doors already bound who floods; more rules for a table that is never full in use.
- **A second bucket per /48 beside the /56:** more state for a delegation the eviction already makes harmless.
- **A column of its own for the claim** (`answered_at`, #324): a migration for a mark `outcome` can carry, since the claim's deadline lives in `expires_at` and the attach overwrites the mark anyway.
- **Deleting the attempt at its callback** (#324's other way): the attach and the exchange need the row.
