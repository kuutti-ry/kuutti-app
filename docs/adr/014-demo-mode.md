# ADR-014: Demo mode: the shortcut lives in the mock bank

- Status: accepted Amended by ADR-018 on 2026-10-08: staging is the demo environment, the demo commands are in the image as files of their own (§10), the personas' stories are written on staging by a job inside the API's container that derives the hash with the container's own key (§12), and `--env staging` is accepted from inside that container (§11).
- Date: 2026-09-27
- Follows: TD-1 (every account is bank-verified), TD-7 (re-registration), TD-14 (age from year and month), TD-19 (seeded environments), CLAUDE.md rules 1, 3 and 8 and the Testing section, `.claude/rules/infra.md` (the mock IdP is local), `docs/vendors/telia.md`; issue #73

## Context

Every M3 feature is tested by hand against an account created through the mock bank, and until now that began with typing a JSON document of claims into the mock's login form, `acr` and `amr` included, because the configuration that was meant to add them never did. A demo of the first ten minutes needs the same beginning, repeatably and on camera. #73 asks for named personas, a synthetic population, photos through the real pipeline and a one-command reset.

The issue's first plan for the personas was a `demo=<persona>` query on `GET /auth/start`, forwarded to the bank as `login_hint` when the issuer is the mock, and a persona picker in development builds of the app. Two things stand against it. It does not work: measured on the pinned version of navikt/mock-oauth2-server, a `requestMappings` entry on `login_hint` adds nothing to a login through the form, whether the parameter is sent with the authorize request or with the token request. And it would have put a branch in the login route and a picker in the app, each of which must then be proven absent where it matters.

## Decision

1. **The personas are persons of the mock bank, and nothing else knows them.** The mock serves a login page of ours (`loginPagePath`): a button per persona, and the form for arbitrary claims below. A button posts what the server's own form posts, a name and the claims. The API's login and the app are unchanged: no `demo` parameter, no login route, no picker. The personas are not exported from `@kuutti/db` either, so nothing of them is on the API's import graph. Where there is no mock bank there are no personas: staging and production identify through Telia, and a preview, which may never use the real broker (`docs/vendors/telia.md`), has no mock deployed beside it today, so bank identification is off there. Deploying a mock bank anywhere public is a decision of its own and needs its own ADR: its form lets anybody be anybody, with this page or without.
2. **Everything after the bank is the product.** The OIDC exchange, the parsing of the code, the HMAC, the age rule and the re-registration rule run for a persona as for anybody. A persona that must be refused (17 years old, banned, inside the waiting time) is refused by the code that refuses people.
3. **Artificial codes.** A persona's personal identity code has an individual number of 900 to 999, which the population register never gives to a person. Rule 1 is about real codes; these cannot be one.
4. **Two kinds of persona.** Eight are born on a fixed day and are the same identity for ever, so the seed can give them a history. Four are born relative to the day of the login (18 last month, 18 this month, 17, 99), so the age holds whenever the demo runs; their identity changes as the months pass, and they carry no history.

   Amended 2026-10-08 (#140): the eight born on a fixed day carry the codes of the test persons of Telia's pre-production bed (`docs/vendors/telia.md` 1.4; nine published codes pass the product's parser, two of the bed's fail the check character and are not used). The mock bank issues locally the very code a test bank returns on staging, so a persona is one identity in each environment, under that environment's key, and a story given on staging (#141) is the same person's; the persona's age follows the code. The ages personas stay the mock bank's alone: no test bank is born relative to today. §3 holds for the bed's codes by the same rule, with individual numbers 905 to 999.
5. **One source, one generated page.** `packages/db/src/seed/personas.ts` holds the personas and `personaClaims`; `pnpm demo:bank` writes `services/mock-idp/login.html` from them. The page is committed, because docker compose mounts it and a clean checkout must start. It computes a code when a button is pressed, so its script says again what `personaClaims` says; one test compares the file with the generator, another runs the page's script against `personaClaims` for every persona over a range of days.
6. **The mock adds no claims.** The `requestMappings` entry on `scope` is removed: it added nothing to a login through the form (measured; it does to a `client_credentials` request, which nothing here makes). A mapping on `code` would add `acr` and `amr` to every login, and was not taken: what is posted is what the token says, so a test can still post another `acr` and see it refused.
7. **Three kinds of data, three homes**, for the parts of #73 that follow. Generators and personas are code and move with the schema: this repository. The population is never stored: a seeded generator makes it. Faces are binary and carry a licence: a repository of their own, pinned here by tag and checksum.
8. **The population is a parameter, made to cross the thresholds** (part B). `generatePopulation({ size, seed, epoch })` in `packages/db/src/seed/population.ts` is pure: no clock, no database, one seeded generator, every date derived from one epoch, so the same command gives the same people on every machine. Who lives where is exact counts, not draws, so the thresholds are crossed by construction: one pond under `gate_k`, one over `majority_share_max`, one where the public counter shows a total and no split, and one where it shows the split. What is drawn is ages, names and words. The words are hand-made lists in three languages, written for the purpose; a test runs every line through the profile's plain-text rule, and another parses every person against the contracts a person's own answers pass (`Gender`, `PreferencesUpdate`, `ProfileUpdate`). `docs/demo/population.md` is the data dictionary.
9. **A synthetic identity cannot be taken for a person, and only a synthetic one is ever removed.** Its `hetu_hmac` is a hash of its label, as the seed's own identities are, so no bank login maps to it and no code was ever hashed; its `broker_subject` carries a mark (`kuutti-demo:`), and it has no time of authentication. The removal needs all three. The mark alone would not do: that column is where a login stores the ID token's `sub` as the broker sent it, and a subject that begins with the mark must never be enough to delete somebody. An identity that carries the mark and is not synthetic is left alone and reported. Writing replaces: after the command, the database holds what the generator says and nothing of an earlier run. Removal deletes rows, which is right for people who never were; the personas, who log in through the bank like anybody, are reset through the erasure path instead (part C).
10. **Behind a door of its own.** The demo tools are `@kuutti/db/demo`, not `@kuutti/db`: the API imports the latter, and the population, like the personas, stays off its import graph (since ADR-018 §7 the demo commands are in the image, each bundled as a file of its own beside `dist/index.js`, which imports none of them). The command lives with the API (`apps/api/scripts/demo-population.ts`, `pnpm demo:population`) because a consent row names the version of the wording in force, which the API knows from the message catalogue. The linter refuses `@kuutti/db/demo` in the apps' own code (`noRestrictedImports`); command lines and tests may import it.
11. **The command does not believe a name.** Synthetic accounts among real people would enter the public counter, count toward the gate and appear on cards as bank-verified. So the command goes ahead only in `development`, `test` or `preview` (an allow-list, by `--env` and by `APP_ENV`, both when both are given), refuses any argument it does not know or is given twice, and, because where the rows go is decided by `DATABASE_URL` alone, asks the server it is connected to what it is before it writes or removes: a managed server (RDS, known by the role only RDS has) is refused unless the database is a pull request's own (`kuutti_pr_<n>`) and the environment is `preview`, or the environment is `staging` and the command runs inside staging's container (ADR-018 §3: nothing of the database or the key given by hand). A rule on the host would not have done: staging and production are reached through a tunnel on 127.0.0.1, under the same database name as the local one. It prints the target, never a password, before anything is written. The seed's own command keeps its older, weaker check; what it writes is idempotent and small, and tightening it is the maintainer's call.

12. **A persona's history is made the way a person makes one, and unmade through the erasure path** (part C). `pnpm demo:reset` first forgets every persona: each live account goes through `eraseAccount`, the function behind "delete my account", so every reset exercises the erasure; then what erasure keeps of a person (the tombstone, the consent rows, the identity with its count of deletions and its waiting time) is deleted too, which is right for a persona and is never done for a person. Then the six histories are given: the command logs the persona in at the mock bank and sends the answers of onboarding and the profile through the API's own routes. No script computes an identity's hash; the key never leaves the API (on staging the job of ADR-018 §2 is the API's own code in the API's container with the API's configuration, and derives the personas' hashes there, from artificial codes only). What no route can do, because no person can, is done in the database afterwards and is two statements: a consent is given the version of an older wording, and an identity is banned as a moderator's decision will ban it. A persona is known by what the mock bank called it (the subject is the persona's name and the method is the mock bank's). Both are what a broker sent, which is less than §9 asks of the population; what keeps the command from people is where it may run. It looks before it acts, and everything it touches is on this computer: development or test; an API and a bank on a loopback address, so a persona's claims are posted to the mock bank and to nobody else, and the bank's way back is followed to `/auth/callback` and nowhere else; configuration from the process's own environment, never from a parameter store; a database server that is not a deployed one (§11); no proxy for the command's own requests; an object store at `localhost`, a loopback address or one of the computer's own addresses, or none while no persona has a photo, since erasure deletes objects and an endpoint is whatever the configuration says (any other name is refused: what it resolves to can change between the question and the deletion), and addressed by path in a bucket that is a name, since the client otherwise makes a host of the bucket's name or follows an ARN to an endpoint of its own; and, where histories are to be given, an API that answers `/health` itself, as ours does, sends a login to a bank on this computer, and serves the command's own database, asked before anybody is erased. The last is known by the login begun for the question before it: the API wrote a row for it, and the command finds that row through its own connection and takes it away again; an API of another database would be given the histories while the personas are erased in this one. What an address cannot tell is a port of this computer that is forwarded to a store somewhere else; the database is asked what it is (§11), the store has no such answer to give. A persona that holds a staff row (a moderator's role, a staff session that has not ended, a line in the audit log, a photo decision) is left alone, whole, and named: erasing it and failing on the deletion afterwards would leave a persona no later reset could repair. A staff session that was revoked or has run out is deleted with the persona, by the rule of the API's own nightly sweep, so that a persona whose role was taken away is reset at once. The forgetting is one transaction in which the personas' identity rows are locked from the question to the deletion: whatever makes a persona staff names the identity by a foreign key, and writing it waits for that lock, so a role granted while the reset runs is seen by the question or finds the persona gone. No row of a photo goes while its objects stay, since the rows are what names them, and three questions hold that, each stopping the reset with everybody as they were. With no object store configured, a persona with photos is not erased. With one, the store is asked before anybody is erased whether it holds the personas' photos: a store on this computer need not be the one the API wrote to, and in another one the deletion of what is not there succeeds. And after each erasure the objects it deleted are counted against what it had to delete: the erasure path forgives a store that fails, as it must for a person who leaves, and answers 0; the reset throws, and the transaction takes the rows back. What that leaves is the other direction, rows whose objects are gone: a reset taken back after some objects had been deleted, or a stand-in whose directory was emptied. The store then does not hold the photos, the reset refuses, and `--objects-lost` is how the developer says that they are lost and not elsewhere. The two direct writes name the account and, beside it, the persona at the mock bank, and each must have met its row.

## Consequences

- `services/mock-idp/{config.json,login.html,README.md,verify.ts}`, `docker-compose.yml` (the mock's read-only mount is the directory now, not a file), `packages/db/src/seed/{personas,bank-page}.ts`, `packages/db/src/cli/demo-bank.ts`, `pnpm demo:bank`. No table, no route, no change in either app.
- What keeps a deployed API from a mock issuer is its configuration, not its code: `parseConfig` accepts any issuer in any environment. That is older than this decision and not changed by it; it is raised with the maintainer separately.
- The personas' histories (part B of #73) must stay out of `packages/db/src/seed.ts`, which the API bundles and runs at a preview's boot: they belong to the seed's command line only.
- The bank's names (given and family name) are in the claims, as the real broker sends them, and the product stores none (rule 3). A persona with å or ö in the name shows that they arrive whole and go nowhere.
- A person who was 17 or "18 this month" on the day of a demo is a different identity next month. That is the price of an age that holds.
- For the maintainer, from the review of part C: a consent row is rewritten for one persona, which ADR-010 says is never done to a person's; inserting the older row instead would leave the account unable to become active, so the rewrite is the better imitation. And "a deployed server" means a managed one (RDS): a deployed plain PostgreSQL would pass the question.
- A second reset within a minute of the first waits for the API's rate limit and takes up to a minute; the first takes a couple of seconds.
- Part C adds no table and no route either: `packages/db/src/seed/histories.ts`, `apps/api/scripts/demo/{bank,histories,reset}.ts`, `apps/api/scripts/demo-reset.ts`, and tests under `apps/api/scripts/`, which the API's test run now includes.
- Part B adds no table and no route: `packages/db/src/seed/{rng,words,population,write-population,demo}.ts`, `@kuutti/schema` as a dependency of `@kuutti/db` (the generator reads the field registry, so an option that leaves the registry leaves the population), `apps/api/scripts/demo-population.ts`.
- After a write or a removal the command empties `waitlist_snapshot` and counts anew, so the counter of #54 shows the ponds as they are now. ADR-013 forbids exactly that in a deployed environment, where the first count after it could lie less than k people from what was last said; here nobody is anybody, and the command has asked the server what it is.
- Nobody in the population has a photo until `--photos` gives them faces of the release (#142); without it everybody counts as finishing.
- The population has no research consents and no research mapping rows: the product writes the two together, and nobody here takes part.
- With the photos (#142): a write or a removal leaves the pictures' objects without a row, so the command deletes the orphans through the media slice afterwards (`deleteOrphanedObjects`) and refuses while there are pictures and no store; a synthetic identity must never be given a moderator's role, because a row it wrote into the append-only `audit_log` would make the population impossible to remove (the removal fails whole on the foreign key, which is the safe way to fail).
- The photos came with #142: a release of the private repository `kuutti-ry/kuutti-app-demo-photos`, pinned here by tag and checksum (`packages/db/src/seed/photos-manifest.ts`, `pnpm demo:assets`), loaded through the upload pipeline for the personas' stories (Sanna, Noa and Kerttu, with Noa's four negatives for the queue) and for the population (`--photos`); locally the faces of a story are approved by a named statement, as the ban is, since the local check queues everything and a persona cannot be a moderator; on staging the container's check decides. Still to come under #73: the storyboard (#144).
