# ADR-057: Google Play: the staging app on the internal testing track first

- Status: proposed (#193, written on 2026-10-27, the day the association's Play developer account was approved, and on the maintainer's answers of that day: `eas.json` out of the native fingerprint, Google Cloud through `gcloud`; the profile, the submission and the runbooks built as written here; the steps in Play Console and Google Cloud are the maintainer's, and so is accepting it)
- Date: 2026-10-27
- Follows: TD-2 (Expo and EAS as the native shell and the update channel), TD-4 (the accounts belong to the association), ADR-004 §3 and §4 (write access is the trust of the staging channel; signing returns before a production build reaches people outside the team), ADR-018 (staging holds test persons only), ADR-028 (the counted version; `app.json`'s version follows at the native batch), ADR-049 (production has no bank identification yet; the release gate is not waived), ADR-056 §1 (attestation's second trigger), rules/i18n.md (the release gate), rules/mobile.md (native changes are batched), CLAUDE.md (GitHub Actions reach clouds by OIDC only); issues #193, #184, #188, #299

## Context

On 2026-10-27 Google approved the association's Play developer account: an organisation account with the developer name Kuutti ry, owned by the maintainer's login at the association's Google Workspace. #193 wants a tagged production build to reach a closed track through `eas submit`. The production app cannot go yet:

- the release gate refuses a production build while Finnish texts wait for their native review, 1,186 of them on this day, and the gate is not waived (ADR-049 §2);
- production has no bank identification (ADR-049), so nobody could sign in to it;
- updates are not signed, and ADR-004 §4 reopens that before a production build reaches anyone outside the team.

What can be proved now is everything before those: the app in Play, its registration, the signing, the upload and the pipeline. The staging app can carry it. It signs in through Telia's test bed with test persons (ADR-018), and the team already runs it as the preview APK.

Google's side, as read on 2026-10-27 by three research passes and a fact-check of each (sources in `docs/vendors/google-play.md`):

- **Registration.** Since 30 September 2026 every app on Play is to be registered to its developer under Android developer verification, and unregistered ones are to be removed. Play Console's Create app now asks for the package name, which is permanent, and registers it to the account then; Play's keys follow at the first upload. A name installed on certified phones before the Play app existed, as `fi.kuutti.app` may be through the team's APKs, can be refused there until the account proves it holds a signing key for the name: a release APK signed with it, carrying a token from the console in `assets/adi-registration.properties`. Below 50 known installs any key will do, and the first to register wins.
- **Enforcement on phones.** From 30 September 2026 in Brazil, Indonesia, Singapore and Thailand, for installs from participating stores; elsewhere, sideloaded APKs included, from 2027, with no date for Finland. adb installs stay exempt. A key that signs builds outside Play, as EAS's signs the development and preview APKs, is registered as an additional key of the package.
- **Signing.** A new app is enrolled in Play App Signing with Google-generated keys, in 2026 a hybrid set: a classical RSA key for Android 16 and lower, a classical and an ML-DSA pair for Android 17 and later. The key that signs the first uploaded bundle becomes the upload key. Until a release reaches open testing or production, the app signing key can still be replaced, for every install, by the developer's own; after that only Google's yearly key upgrade, for Android 13 and later, changes it. A Play install and an APK signed with another key cannot update each other.
- **Internal testing.** Up to 100 testers by e-mail list, kept in the console by hand. A release is not reviewed, except the app's first when its setup is complete by then; with the setup incomplete it reaches the testers at once. Neither the store listing nor an app content declaration is needed for it.
- **The API.** No API creates an app. Whether the first bundle must go through the console is disputed: Google's Edits guide says so, while Expo tested in July 2026 that the first `eas submit` to internal testing works on a new app.
- **Credentials.** EAS Submit takes only a service account's JSON key, which EAS stores per application id; it has no OIDC and no Workload Identity Federation. A Google Cloud organisation created on or after 3 May 2024 refuses to create such a key until its policy is lifted for the project, and the association's Workspace dates from October 2026.

## Decision

1. **The staging app goes to Play first.** A build profile `staging` in `eas.json`: store distribution, so an app bundle; the preview build's channel `staging` and EAS environment `preview`; and a version code that EAS counts up (`autoIncrement` on the remote counter that every profile of `fi.kuutti.app` shares, so Play always gets a higher number). `eas-build.yml` builds it only when the maintainer starts the workflow from `main`, and for Android alone until the association's Apple account can take it to TestFlight (#193). The release gate does not run for it: the bundle reaches the team, never the public.
2. **On the internal testing track, for the team alone.** The testers' list holds the people who may run the staging channel's unsigned updates today (ADR-004 §3): the team who install the preview APK. Nobody else is added while ADR-004 §4 is open.
3. **EAS submits, with a key that only EAS holds.** `--auto-submit` gives each staging bundle to the submit profile `staging` (track `internal`, status `completed`), and EAS uploads it once it is built. The key is a JSON key of a service account in the association's Google Cloud project: the maintainer creates it, uploads it to EAS and deletes it from the disk. In Play Console the service account may, on this app alone, view it and release it to testing tracks, never to production. No GitHub environment holds a Google credential, so CI's OIDC-only rule holds where it applies. The key is long-lived and sits at Expo beside the upload key, and two things bound what it can do:
   - **EAS uses it for any holder of `EXPO_TOKEN`**, so for anyone with write access (ADR-004 §3), on any testing track, with the upload key that every cloud build is handed. That is the update path's trust already: whoever holds the token can change what installed phones run without any build.
   - **The same permission uploads to internal app sharing**, which takes a bundle signed with any key, shows in no track's history, and hands a link to whoever its list admits. The list is the team's, set before the key exists (`docs/vendors/google-play.md`, step 3).

   So, while the app's setup is incomplete (Open 1), the key reaches the team's phones and nobody else's, as the update path does. A closed track waits for this credential to be decided again (point 7).
4. **Play's own signing keys, for now.** The app is enrolled with the keys Google generates, and EAS's keystore of `fi.kuutti.app` becomes the upload key. The choice stays open until the first open-testing or production release, the last moment the key can be replaced for every install.
5. **The package name is proved with EAS's key, should Create app refuse it.** The proof is one release APK of the `preview` profile, built on EAS from a commit that is never pushed and carries the console's token in its assets, so the private key never leaves EAS. Either way EAS's key is then added to the package as the key of the builds outside Play, before Google's checks reach Finland.
6. **The first internal release comes before the app's setup.** The store listing and the app content declarations wait until the first release has rolled out, so that it is not held for Google's review. If EAS's first submission is refused, because the API does not know the app yet or the app is still a draft, the maintainer uploads that bundle in the console once. Should Google go on refusing completed releases while the setup is incomplete, the submit profile sends drafts, which the maintainer rolls out, until #188's setup is done.
7. **Production builds are not submitted yet.** The submit profile `production` stays empty and a release tag starts no submission until ADR-004 §4 is settled, the release gate passes, production has bank identification, the closed track and its testers exist, and #188's declarations and #299's way in for the reviewers are done. The Play credential is decided again then: a keyless upload from a job that admits `main` alone (Alternatives), or this key behind ADR-004 §3's reviewer. The change that adds it is #193's.
8. **`eas.json` leaves the native fingerprint.** `@expo/fingerprint` hashes `eas.json` whole, so the `staging` profile alone would orphan every installed build, and so would each later edit, production's submission and TestFlight's among them. `fingerprint.config.js` ignores it. What in it could change a build's native side, a profile's `env`, `prebuildCommand` or custom build `config`, `plugins/fingerprint.test.js` refuses; one that is needed brings `eas.json` back into the fingerprint first. This change still moves the fingerprint once, from main's `d842d08c` to `8b49eb08`, by the maintainer's choice of 2026-10-27.

## Consequences

- Google receives each bundle, the testers' addresses and what Play itself collects on the phones that install from it (`docs/vendors/google-play.md`). The app adds no Google library of its own.
- A phone holds either Play's copy or an APK from expo.dev, not both: they are signed with different keys and cannot update each other. A tester uninstalls to switch, and loses what the app kept on the phone, the session among it.
- Each staging bundle is one of the free tier's 15 Android builds a month.
- The merge moves the fingerprint once (point 8): its push to `main` starts a development build, and every installed development and preview build stops receiving updates until it is replaced.
- A new long-lived credential, the service account's key, at Expo: `docs/runbooks/custody.md`, and `rotation.md`, section 14, and section 10 for a leak of `EXPO_TOKEN`, which reaches it too.
- Verified links (#184) list Play's three signing fingerprints beside EAS's in `assetlinks.json`, and a Firebase key for push restricted by signing certificate (#102) needs Play's too.
- The version name stays `0.0.0` until #184's native batch; testers see it in Play.
- Google's pre-launch robots run each uploaded bundle on test phones. In the staging app they stop at the bank login.
- ADR-056 §1's second trigger reads "Kuutti is distributed through Google Play". This record takes it to mean the production app on Play, which waits for point 7; whether the staging app on internal testing already counts is the maintainer's reading (ADR-056: starting §2 is his).
- The Expo template's `SYSTEM_ALERT_WINDOW` is in every release build's manifest, though nothing uses it. Leaving it out is an `app.json` change, so it belongs to #184's native batch.

## Alternatives considered

- **The production profile first.** Nobody could sign in, and its first bundle would need the release gate waived.
- **A keyless upload from GitHub Actions:** Workload Identity Federation from a job's OIDC token to the service account, the job in an environment that admits `main` alone, and an upload after fetching the bundle from EAS (r0adkll/upload-google-play, fastlane's supply, or the Edits API by hand). No key would exist anywhere, and only `main` could upload, where the stored key serves every holder of `EXPO_TOKEN`. But the job waits out the build in the free tier's queue, an action or a script of our own holds Play rights, the bundle crosses GitHub's runner, and Google Cloud needs a workload identity pool. While `EXPO_TOKEN` already lets any branch change what the team's phones run (ADR-004 §3), the narrower boundary buys little for the team's own phones. It is the likely answer when point 7's closed track comes, or if Expo should no longer hold the key.
- **EAS's keystore as Play's app signing key.** Play's copy and the expo.dev APKs could then replace each other, and one key would be registered. But the one key that signs every install would sit at Expo, Google advises an upload key apart from the signing key, and Android 17's hybrid signing may be given up (Google does not say). Open until the first open-testing release (point 4).
- **A separate application id for the development and preview builds** (`fi.kuutti.app.dev`), so that both live on one phone. A native change of its own, with the bank's return to the app and the verified links (#184) to rework for a second id.
- **The team on expo.dev's APKs alone, as today.** Developer verification would still want EAS's key registered, and nothing of Play's path would be proved before the beta.

## Open, the maintainer's

1. Play's own signing keys or EAS's (point 4), before the first open-testing or production release. Since any holder of `EXPO_TOKEN` could submit such a release once the app's setup is complete (point 3), the choice comes before the setup.
2. Whether the staging app on internal testing is ADR-056 §1's second trigger.
3. When the production app goes to a closed track, and to whom (#193).
