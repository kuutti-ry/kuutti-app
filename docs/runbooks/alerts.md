# Alerts: what each one means and the first three commands

Every alarm of `infra/modules/observability` (#11) publishes to the environment's SNS topic (`kuutti-<env>-alerts`, eu-central-1) and the billing guard rails to `kuutti-billing-alerts` (us-east-1). Both mail the subscribed address; OK transitions mail as well, so a single "ALARM" without an "OK" means it is still broken. Sign in first: `pnpm aws:login`. `<env>` is `staging` or `prod`, `<id>` the instance id from `tofu output instance_id` in `infra/envs/<env>`.

| alarm | it means | first three commands |
|---|---|---|
| `kuutti-<env>-instance-status-check-failed` | The box fails EC2's hardware or OS check, or is stopped. Deploys and previews are down. | `aws ec2 describe-instance-status --instance-ids <id> --include-all-instances` · `aws ec2 get-console-output --instance-id <id> --latest --output text \| tail -50` · `aws ec2 reboot-instances --instance-ids <id>` (a stop/start moves it to new hardware if the reboot does not help; the Elastic IP follows) |
| `kuutti-<env>-instance-cpu-credits-low` | The t4g box has burned its burst credits: it slows to baseline, or in unlimited mode starts billing per vCPU-hour. Usually a runaway process or a preview build loop. | `aws cloudwatch get-metric-statistics --namespace AWS/EC2 --metric-name CPUUtilization --dimensions Name=InstanceId,Value=<id> --statistics Average --period 300 --start-time $(date -u -v-3H +%FT%TZ) --end-time $(date -u +%FT%TZ)` · `aws ssm start-session --target <id>` then `top -o %CPU` · `docker stats --no-stream` on the box |
| `kuutti-<env>-memory-low` | The box has had under 200 MB available for five minutes, or has stopped saying how much: `MemAvailable`, pushed every minute by a cron line of the headroom script (#77, ADR-046). A box that has never pushed (after the apply that created the alarm, until the headroom document has run; after a rebuild, until first boot has) is in ALARM within a minute or two (`infra/README.md`, The box's headroom). Twice before (2026-09-27, 2026-10-08) this came before the API went unreachable: previews piling up, deploys at once, Dokploy growing. | `aws ssm start-session --target <id>` then `free -m` (swap in use is fine, swap full is not) and `sudo docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}'` · `sudo dmesg -T \| grep -i "killed process" \| tail` and `sudo docker service ps dokploy` (Dokploy restarted by its limit, exit code 134 or `OOMKilled`, is the limit at work; the API killed is not) and `sudo docker service ls`, then `sudo docker service scale <api-pr-n-…>=0` for a preview whose pull request is closed (the sweep removes it later, ADR-012) · no data at all: `cat /var/log/kuutti-memory-metric.log` (the last push's error, empty after a good one) and `ls /etc/cron.d/kuutti-memory-metric`; missing, send the headroom document |
| `kuutti-<env>-db-free-storage-low` | Under 2 GB free on RDS. Storage autoscaling stops at `max_allocated_storage_gb`; a full disk stops writes. | `aws rds describe-db-instances --db-instance-identifier kuutti-<env> --query 'DBInstances[0].[AllocatedStorage,MaxAllocatedStorage]'` · from the box: `psql ... -c "select pg_size_pretty(pg_database_size('kuutti'))"` and `select relname, pg_size_pretty(pg_total_relation_size(oid)) from pg_class order by 2 desc limit 10` · raise `max_allocated_storage_gb` in `infra/envs/<env>` and let CI apply |
| `kuutti-<env>-db-cpu-credits-low` | The db.t4g instance is out of burst credits; every query slows. A missing index or a preview running a load test. | `aws rds describe-db-log-files --db-instance-identifier kuutti-<env>` · Performance Insights in the console (7 days free) · from the box: `select query, calls, mean_exec_time from pg_stat_statements order by total_exec_time desc limit 10` |
| `kuutti-<env>-api-5xx` | Five or more 5xx answers in five minutes. The API is up (it logged them); something behind it is not, or a deploy shipped a bug. | Logs Insights saved query `kuutti-<env>/errors-by-route` · `aws logs tail /kuutti/<env>/api --since 30m --filter-pattern '{ $.status >= 500 }'` · Sentry, project `api`, filter by `requestId` from the log line |
| `kuutti-<env>-api-unreachable` (us-east-1) | Route 53's checkers cannot get `"status":"ok"` from `https://api.<env>.<domain>/health` for two minutes: the API service has no running task, Traefik is not routing, or the box is down. The one alarm that sees a dead container (#29). Both outages of #77 (2026-09-27, 2026-10-08) were this alarm with the box out of memory, so memory comes first. | `curl -sS https://api.<env>.kuutti.app/health` · `aws ssm start-session --target <id>` then `free -m`, `sudo dmesg -T \| grep -i "killed process" \| tail` and `sudo docker stats --no-stream` (out of memory: the `memory-low` row; a preview of a closed pull request still running is the fastest relief, `sudo docker service scale <api-pr-n-…>=0`, as on 2026-10-08) · `sudo docker service ls` and `sudo docker service logs --tail 100 <env>-api-<id>` (the API is a Swarm service under Dokploy: a stopped task is replaced within seconds and is no outage; the service at 0 replicas or a task that cannot start is) · `sudo docker service scale <env>-api-<id>=1`, or redeploy in Dokploy; if the instance itself is down, the status-check row applies. Proven 2026-09-22: scale to 0 → ALARM in 4 min 10 s; scale to 1 → OK 4 min after /health answered |
| `kuutti-<env>-nightly-job-failed` | A nightly job logged `nightly job failed`, or the prune dropped research events whose days the copy does not have (`research events dropped without their copy`, #194, ADR-029 §6). The night's other jobs still ran. A failed `research-export` catches up by itself on a later night while the table holds the days; one left failing loses days at the prune about sixty days on. A preview's container runs the same jobs into the same log group, under its own stream. | `aws logs tail /kuutti/<env>/api --since 24h --filter-pattern '{ ($.msg = "nightly job failed") \|\| ($.msg = "research events dropped without their copy") }'` (the `job`, the `err.type` and the stream, named after the container) · `aws logs tail /kuutti/<env>/api --since 24h --filter-pattern '{ $.job = "research-export" }'` (the export's own line: days written, rows, dropped) · AccessDenied from S3 under `research/`: `modules/research` not applied, or its write-once condition (`infra/README.md`, Research copy) |
| `kuutti-estimated-charges`, budget 80 % / 100 % | Spend is past the budget (TD-4). | Cost Explorer by service · `aws ce get-cost-and-usage` for the month · check nothing runs outside eu-central-1 (`aws ec2 describe-instances --region <r>` per region) |

The probe's alarm and topic live in us-east-1 because that is where Route 53 publishes health-check metrics; its email subscription is confirmed separately from the regional one. `aws cloudwatch describe-alarms --region us-east-1 --alarm-name-prefix kuutti-<env>` shows it.

## Logs

`aws logs tail /kuutti/<env>/api --follow` shows the JSON lines pino writes: `requestId`, `route`, `status`, `durationMs` per request, `err.type` and a redacted stack on errors. Saved Logs Insights queries in the console: `errors-by-route`, `p95-duration-by-route`, `boot-and-fatal`. Retention is 30 days.

## Delivery test

`aws sns publish --topic-arn "$(cd infra/envs/<env> && tofu output -raw alerts_topic_arn)" --subject 'kuutti alert test' --message 'delivery check'`. If nothing arrives, the subscription is still pending: `aws sns list-subscriptions-by-topic --topic-arn <arn>` shows `PendingConfirmation` until the link in AWS's mail is followed.
