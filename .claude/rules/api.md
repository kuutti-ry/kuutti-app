# API (Hono on Node) rules

One process: HTTP routes, WebSockets through `@hono/node-server`'s own upgrade over `ws` (`@hono/node-ws` is deprecated; ADR-031 §9), and the nightly jobs (round builder at 04:00, events to Parquet, retention pruning) as cron inside the same container. Consult `https://hono.dev/llms.txt` for framework specifics.

## Routes

- Every route validates input with a schema from `packages/schema` at the boundary: body, query, params, and any header used for logic. Responses are typed from the same contracts.
- RPC style across the boundary is an open decision (lean: generated types via `@hono/zod-openapi`). Do not introduce `hc<typeof app>` or a hand-written client without an ADR.
- Machine callers (the Telia redirect, SNS bounce notifications) get plain HTTP endpoints with their own validation.
- Product routes refuse browser origins. There is no CORS except an allowlist for the admin SPA and the waitlist site.
- Rate limits are in-process fixed windows and fail closed: a request with no address shares one bucket. No Redis (TD-3). Keys (ADR-026): the client address the trusted proxy reports (ADR-008 §5), IPv6 by its /64, until a guard admits the request; then its person, the account or the staff identity, and the address gets its count back. A new guard is built with `limit: perPerson` (`app.ts`), so one person has one budget; a new route that ends a session or the account joins `ENDS_SESSION` there, outside the person's budget and kept on the address's. The sign-in doors are the two starts (`/auth/start`, `/admin/auth/start`): their own window per address, IPv6 by its /56, checked before anything is written or signed; the exchanges are not doors. A refused start, by any limit, redirects with `error=auth_rate_limited` (`refuseSignInStart`), never a JSON 429 in the system browser. `auth_request`'s ceiling evicts the oldest attempts the bank has not answered (no code, no callback under way) rather than refusing (ADR-026 §6). The numbers are config, `RATE_LIMIT_PER_MINUTE` and `SIGN_IN_RATE_LIMIT_PER_MINUTE` (SSM), not `matching_config`.

## Identity and auth

- OIDC through `@kuutti-ry/tunnistus-oidc` (ADR-017; `openid-client` and `jose` underneath) as Telia specifies it (docs/vendors/telia.md): a signed request object (RS256, our `sig` key, `acr_values` mandatory), `private_key_jwt` at the token endpoint, and an ID token that arrives encrypted to our `enc` key and signed by Telia: decrypt, then verify `state`, `nonce`, the signature via the issuer JWKS, `iss`, `aud`, `exp`, and the `acr` expected for FTN. Broker endpoints and keys come from discovery at boot and rotate on Telia's schedule; nothing is pinned.
- The hetu lives only inside the callback handler: parse (accept all century separators `+ - A-F Y X W V U`), check 18+, derive `birth_year` and `birth_month`, compute `HMAC-SHA256(hetu)` with the SSM key, then discard. Never log it and never pass it to a function that could retain it.
- Re-registration at the callback per TD-7: banned or suspended refuse and increment `refused_attempts`, a suspension with the day it ends (`suspension_ends_at`); inside `reregister_after` refuse with the date; otherwise a fresh account with nothing restored.
- The app's exchange is bound to its start (ADR-027): `code_challenge` at `/auth/start`, required; `verifier` at `/auth/exchange`; one UPDATE (`consumeAppCode`) spends the code only with its challenge, and a wrong verifier leaves it unspent. Every refusal is `auth_code_used`. The staff path is not bound. This is not Telia's PKCE: nothing new goes to the broker.
- Session tokens: random 256-bit, hashed at rest, constant-time compare. Device-bound refresh tokens. Admin sessions are 8 hours with no refresh.
- One identity row per `hetu_hmac`, at most one live account per identity. A ban is set on the identity. `account.state` and `identity.standing` change because of a sanction only through `settleStanding` (`identity/standing.ts`), from the sanctions still open (ADR-024 §2); never write either by hand.

## Data access

- Every user-data query is scoped by the session `account_id` in the query. The reviewer greps for it.
- Drizzle query builder only; a raw `sql` template needs a comment explaining why.
- Visibility is computed, never stored. Inactivity is a timestamp.

## Media

- Uploads: 10 MB cap, sharp with `limitInputPixels`, `p-limit` at vCPU count, 503 with `Retry-After` above the limit. Strip EXIF. Generate thumb 200x200, card 800x1067, full 1600 long edge, WebP, content-addressed keys. Never persist the original.
- Rekognition moderation on upload, never auto-delete. What the check is sure of it rejects itself and the owner is told why: a hard label at its group's reject line, no face, several faces; what it is unsure of goes to the human queue (ADR-006 §2, #206, #253), and what nobody there decides within `photo_queue_reject_days` the night rejects as `not_reviewed` (#376), a reason no moderator chooses. A person may also take down an approved profile photo (#477): the decision route's own `take_down`, keyed on the approved state, never the queue's `reject` read off the state found; a rejection with a moderator's reason, never a sanction, never a deletion, and never a photo sent in a conversation. Keep the moderators' load to what the check is unsure of; the groups and their lines live in `media/label-groups.ts` and `matching_config`. A photo sent in a conversation (`purpose = message`, #350, ADR-031 §10) is checked before anything is stored, on its full size, without the face rules: what the check is sure of is refused and nothing stored, what it is unsure of is delivered with no human queue, and one no check saw is delivered only where `deliverUnchecked` says it is a developer's machine or a test. Every profile read asks for `purpose = 'profile'`.
- Signed CloudFront URLs: 15-minute TTL, issued only inside rate-limited responses (never in a socket frame), every issuance logged (`account_id`, `photo_id`, variant, time). URL issuance counts against the exposure budget, except a photo sent in a conversation (#350, ADR-008, ADR-031 §10): its URLs are issued in a page of the conversation, the read of one message and the send's answer to its sender (201, and 200 for a resend), logged with the purpose `message` and never counted. They end at the next five-minute mark plus fifteen minutes, so they live 15 to 20 minutes; on CloudFront a repeated read inside the five minutes gets the same URL, and the fetch log has one row per viewer, photo and variant in each five-minute window, two reads at the same instant aside.
- The data export (`GET /account/export`, #237, ADR-007 §3) is one zip built in memory: the document, every profile photo's `full` file, and the `full` file of the person's newest hundred photos sent in conversations (#350; a `shortcut:` until the zip is streamed). At most `matching_config exports_per_day` per Finnish day, counted in the statement that records the export; each profile photo read is logged as a `full` fetch, counted, never refused. Each of the person's own lines with a photo carries an object: its file in the zip (null when the zip does not carry it: the object is gone, or the photo is not among the newest hundred), the check's outcome as a profile photo's review is shown (for a sent photo `queued` means the check was unsure and the photo was delivered with no human queue), and its automatic description, in keys and in words in the request's language. Each sent photo's read is logged with the purpose `message`, never counted.

## Events and logs

- `track(name, props)` server-side only, against the zod registry in `packages/schema`. Keyed by `research_id`; carries `consent_version`, pond, and the coarse snapshot. Never message text, never raw `seeks`, never email.
- The research copy (#194, ADR-029): `research-export` writes each closed UTC day once to `research/` in the media bucket (put-if-absent, never rewritten), before the partitions job, and only where media has a bucket, never in a preview, and not in production until the maintainer has answered ADR-029's ninety days (a `shortcut:` in `boot.ts`). A file of a day not yet closed stops the night. A value is released only when the copy carries it for k pseudonyms whose research consent is live that night, one per person (ADR-029 §4); a file never carries the account, the event's id, the stored snapshot or text. The prune checks the copy before dropping a month and drops it anyway (§6).
- Structured logs with `account_id` (on the panel's requests the staff identity, `staffIdentityId`) and request id; never hetu, message text, email, or a client address: a refusal's line names which limit refused, never its key (ADR-026 §7). Errors: generic response body, detail to logs and Sentry, no empty catch.
- A stored contact (#103, ADR-031 §11) is answered to its owner, and to the other person of a conversation only in its detail and its contacts read while the owner shares it there; never in a log line, an error detail, a validation message, an event or a socket frame. The logger redacts `value`; a refusal names the kind; the `contacts` frame names the conversation, and the phone answers it with `GET /conversations/{id}/contacts`, which signs nothing and writes nothing; a share's row holds no value.
- Mail (#385, TD-18, ADR-043) leaves only through `Deps.mailer` (`lib/mail.ts`): SES, the log mailer, or none where `MAIL` is off, and a route that would send answers 503 `mail_unavailable`. Nothing else builds an SES client. Neither the address nor a code reaches a log line, an error detail, an event or Sentry: a failed send is `MailFailed`, the SDK's error name and status alone, since SES names the address in its messages. The log mailer writes the message, code included, to the log, so the configuration refuses it outside development and test. An unconfirmed address is sent nothing but its code; a message is plain text from `messages.yaml` in the request's language, names nobody and carries no link (rule 8).
- Push (#102, ADR-055) leaves only through `Deps.pusher` (`lib/push.ts`): Expo's push service, a log of the kinds (development and test only, as mail's), or none where `PUSH` is off. Whom to tell is the notifications slice's (`notifications/push.ts`); the chat and the round's routes only say when, through callbacks `app.ts` hands them, and the push runs after their answer, so no answer's time says whether anybody was pushed. A push carries one line of the app's words in the device's language and `PushData` (`packages/schema`), its kind alone, never a message's text, a name, an account's id or the conversation, and no token reaches a log line; a failure is logged by its kind and code and changes no answer. A device's token is its session's and goes when the session is revoked (migration 0082's trigger) or deleted.
- The automatic shadow bans (#105, ADR-033) are checked after the triggering request has committed, as one transaction under the person's sanction lock (`lockAccountForSanction`), and change no answer whatever they find: a check that fails logs its kind and the error's code. No line they write names a person: in a report's request the caller is the reporter, and whom they reported reaches no log line (ADR-030 §9). A conversation's openers are read and compared in the chat slice alone (`chat/first-messages.ts`), which hands the safety slice counts and times; nothing derived from a message's words is stored. The machine's ban is the one `audit_log` row with no actor (`audit_log_actor_check`). #86's velocity rules (ADR-041) are three more on the same seam, for the reason `scraping`: after a URL of another person's photo in the card size (never a thumb; another's full size is refused, ADR-056 §3) and after a served read of today's round, handed to those routes by `app.ts`; being on reads, each is measured first without the lock, with the person's standing (`standingOf`), and takes it only when met and the person is in sight, so a ban never slows a later answer. The round's reads live in memory only, never in a table, at most the threshold's worth per account and swept on a timer once a window.
- A report's frozen copy of a conversation (`report_message`, #351, ADR-030 §12) is written by one `INSERT … SELECT` from `message` under the conversation's lock (`copyConversation`, `chat/repo.ts`), so its words never pass through the process. Besides that statement, only the safety slice's hold of the photos it names, the night's prune of them, and the moderators' opened report (`report-queue.ts`, #312) read it (`safety/no-signal.test.ts` lists the files). The one route that answers it is `GET /admin/reports/{id}`, after its `conversation.view` row; a photo it names is signed in full by `GET /admin/reports/{id}/copy/{seq}/photo` after a `photo.view` row, both about the report, never a person, and never to a member of staff who is a party (ADR-030 §6, §9). It is in no log line, error detail, event, frame or export, the reporter's included. A report may point at the one photo it is about (#476, ADR-030 §13): a conversation's at a line the reporter could read of a photo the other person sent (asked through the chat's reads, never the copy), a card's at a profile photo of the card the reporter was shown; one that does not hold is stored as none and changes no answer, and like the note the filing logs no pointer; a moderator's look logs the photo it signs, as every issuance is logged. A card's pointed photo is signed in the card size by `GET /admin/reports/{id}/photo` after a `photo.view` row about the report, never to a party.

## Config and jobs

- Environment validated with zod at boot; a missing key fails the start. Deployed config comes from SSM through the instance role; the local `.env` is read by the runtime only, never by tooling or agents.
- Migrations run in the entrypoint under an advisory lock before the server listens.
- WebSockets: application-level ping/pong (CloudFront documents no idle timeout). The chat's socket (`chat/ws.ts`, ADR-031 §9) authenticates by its first frame, validates every frame against `packages/schema/src/chat-frames.ts`, and is told what changed by Postgres's LISTEN/NOTIFY on commit (migration 0055's triggers, the conversation's narrowed by 0063 to a change of `archived_at` or `closed_at`; `chat/listen.ts`), which also serves a second instance if one ever exists. A notification carries ids and numbers, never text; what a person may see is read through their own participant row. No frame tells a block or a report from an end (ADR-030 §12): a block's notification reaches the blocker's side alone, and the other person hears only the close's own frame, so a new trigger or fan-out must not send them anything an end does not; a close stops both read marks where it found them (`chat/repo.ts`'s `markRead`), since the one who ended a conversation can still open it and its blocker cannot.

## Tests

- `app.request()` per route: happy path, validation failure, unauthenticated, wrong-user. Real Postgres, transaction rolled back per test.
- fast-check property tests for hetu parsing and HMAC derivation. Coverage floor for the API in `vitest.config.ts`, identity's the strictest (ADR-021).
- A test asserts that no PII pattern appears in log output.
