# identity

Bank-ID registration, identity standing, accounts, sessions, re-registration. TD-1, TD-7. Taking a break (#170, ADR-022): `BreakScreen` says what happens and `pauseAccount` on the session provider does it; the sign-in screen says the account is on a break from the provider's notice, and the home screen welcomes an `unpaused` login back once. Your account's actions (`AccountActions`) open "I found someone" (#83, ADR-040), the settings slice's `FoundThemScreen`, by its route: telling Kuutti changes nothing, so this slice holds none of it.

The optional e-mail (#148), a way to stay in touch, confirmed by a code (#385, ADR-043): `EmailCard` holds the address with what the API last answered of it (confirmed, and until when a code waits), on its own Settings screen and among the later screens (`EmailScreen`, which keeps the code's field above the keyboard as a settings screen does, and whose Done leads on to the lock's one offer while it is due). Whether a code waits is the API's last answer, never the phone's clock: a code that runs out while the card is open keeps its field until Confirm's answer says it expired. The API's save sends nothing, so a failed send never fails a save: after a save that leaves the address unconfirmed with no code waiting, the card asks for one code by itself and says "Saved." and then what the send said, until when the code works or why it did not go. Every answer is a fresh notice in an assertive live region and, on iOS, said aloud, so a second code sent within the minute is said again. The six digits are typed on the card. The refusals of the code routes the card has words for (a wrong, spent, expired or missing code, the day's limit, no mail) say them, and any other says the code failed; the two that mean the address changed on another phone, `email_confirmed` and `email_none`, read it again and show what the API holds. An answer takes the field along unless the person has typed in it. `email-client` is the routes, through the typed client.

The screens before the bank (#418, ADR-010 §15): until this phone has recorded the current versions of the terms and the privacy summary, the sign-in screen shows `BeforeSignIn` where the bank button would be. It asks the four norms with both consents (`NormsAndConsents`, which onboarding's welcome step shows too when they are missing after the sign-in), then research as a yes or a no, either of which goes on to the bank. `agreements` holds the answers in memory until the exchange, posts them through `POST /consents` right after it and before the status is read (the terms, the privacy summary, then research on a yes; a no posts nothing), and remembers the versions on the phone (the preference `agreedVersions`), so the next sign-in goes straight to the bank. A post that fails is left to the welcome step; onboarding asks nothing about research, and Settings keeps its switch.

The app's lock (#418, ADR-045), in `lock/`, on the phone only. `LockProvider`, under the session provider, reads the lock once, locks at a cold start and after the person's grace time in the background, and covers the app in the app switcher; whenever there is no session it removes the stored lock, so any sign-out turns it off. `LockScreen` offers the face or finger where chosen, the passcode where set, and always the bank, which is `signOut("lock")`, the same as the fifth wrong passcode, and whose notice the sign-in screen says. `PasscodeField` takes six digits, on the lock and in Settings. `passcode` is the salted SHA-256 and its constant-time compare; `store` keeps the lock and its tries in SecureStore, this device only; `biometrics` asks the phone's prompt with no fallback to the phone's code. `useLock` is what the settings slice's `LockControls` reads and changes, in Settings › Lock and in the one offer after the e-mail (`LockOfferScreen`, `useLockOfferDue`, `markLockOffered`). Nothing of it reaches the API.
