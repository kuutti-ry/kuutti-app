# notifications

Daily round push, in-conversation push, the match push, optional email channel. TD-3, TD-18, ADR-055.

- `NotificationChoices.tsx` (#176, ADR-032): Settings › Notifications, one switch per kind (a new round, messages, matches, moderators' decisions), stored on the server and on until switched off, under the line saying that a push tells only that there is something and the phone's own permission (`PhoneLine.tsx`). The settings slice wraps it in its page.
- `PhoneLine.tsx` (#102, ADR-055 §9): whether this phone lets Kuutti notify it, in words: allowed; refused, with the button to the phone's settings (`Linking.openSettings`); never asked, with the button that shows the phone's own question, dimmed while it is open; or unavailable (the web preview, a phone that could not be read). Read again as the app comes back to the front; a change after the first read is said (VoiceOver told, TalkBack's live region). On the web target the line alone: nothing read, listened for or asked.
- `PushOffer.tsx` (#102, ADR-055 §9): the home screen's one offer of notifications, in the gate card beside Today's round once matching is open: the reason, Allow notifications (the phone's question) and No thanks, of equal weight, both dimmed from a tap until the answer is in; only while the phone was never asked, and never again on this phone after either answer (the preference `pushAsked`).
- `PushNotifications.tsx` (#102, ADR-055 §2, §9): mounted once in the root layout. While signed in it registers the token at every start, on a new device token, on a change of the app's language and whenever the app comes back to the front, which takes a permission given in the phone's settings meanwhile and retries a start that found no network (an identical registration sends nothing); a push in front is a banner and in the list, silent, never a badge; a tap opens what `PushData`, the kind alone, says: the conversations (`/chats`) for a message or a match, today's round for the round; once, after the lock if it holds the screens (`useLock().holding`: shown, deciding at a cold start, or covering them while away), and nothing while signed out, after the lock was left through the bank, or for data that does not parse, a conversation's id among it; a sign-out clears the phone's list of pushes (`dismissAllNotificationsAsync`). Nothing on the web target.
- `phone.ts` (#102): the phone's side. `permissionOf` and `readPermission` (the permission in the app's words: iOS by its own status, Android by the root one), `askPermission` (Android's `default` channel first, then the question for the banner and the sound, never the badge), `registerPush` (only while allowed, the token and the platform and nothing else, in the app's language, one at a time, none identical to the last one the API took for the session, nothing after a sign-out; a failure reported to Sentry, never shown), `unregisterPush` (the phone drops its device token, `unregisterForNotificationsAsync`, after a sign-out whose logout the API did not take, which the root layout hands the session provider as `onLogoutUnheard`: the server's session and its token live on; Apple or Google then stop delivering to the phone, Expo's next ticket for it should say `DeviceNotRegistered` and the API deletes the row, which on iOS, where the phone may be handed the same token again, is not certain; in turn with the registrations; nothing on the web; a failure reported, never thrown).
- `usePhonePermission.ts` (#102): the permission for a screen, read as it opens and again in front, with `ask` and `asking` while the question is open, unavailable and inert on the web target; a yes to its question registers the token at once, and one given in the phone's settings is `PushNotifications`' to register.
- `client.ts`: `GET /account/notifications`, `PUT /account/notifications/{kind}`, `GET /notices`, `POST /notices/{id}/read`, `PUT /push-token` (with the app's language as `Accept-Language`).
