# profile

Onboarding, profile fields and prompts, completeness. TD-16. The photo tips are the media slice's since #287.

What others see is the person's choice, field by field (#515, ADR-019 §2): a card shows every answer until `FieldEditor`'s title row says Hide. The set saves with the rest of the screen, merged key by key like the answers (`useProfile`). It changes the card and nothing else.

The home (#514, ADR-061) is no field of the registry and no part of the draft: `PlaceEditor` holds the postal code with its autocomplete, read from `@kuutti/schema/postal-areas` on the phone, and what the card will say; onboarding's two home steps and `PlaceScreen` stand on those, and `saveHome` writes through its own route. The digits stay in `PlacePicker`'s state until a row is tapped, go in that one body, and leave with the save. `useProfile` reads the home's names and never holds them in what it sends. A card says a name, and a round's card the band its entry froze, handed in by `RoundScreen`.

The gender (#552) is the account's and no part of the draft either: `gender/GenderScreen` at `/profile/gender`, opened from its own row beside the home, reads it with its limit from `GET /onboarding` (`fetchOwnGender`) and saves through `saveGender` on leaving, with `useSaveOnLeave`. Onboarding's gender step asks with the same `GenderChips`. The screen offers the identity label while non-binary is chosen and none is stored, keeps it in its own state so that a held word needs no read to come back, and sends it through `saveChanges` only after the gender was accepted; a change away from non-binary takes it on the API (ADR-019 §1).

What a person seeks is a list of its own (#542): `seek/SeekScreen` at `/profile/seek`, opened from the profile and from the queue's end (ADR-062 §11), so its way back names neither, with each row's answer under onboarding's own question. Whom and the ages are `seek/SeekWhomScreen` and `seek/SeekAgesScreen`, which save on leaving through `useSaveOnLeave`, the sections' way out. What one is here for is the section `intent`, which `LISTED_SECTIONS` leaves off the profile's list so that it has one door. `useSeeking` reads the answers with the consent, and whoever lacks any of them goes back to Home, whose gate sends them to onboarding, which asks: the consent is given on the seeks step and taken back in Settings (ADR-019 §4), never here. `PUT /preferences` goes through `savePreferences` here, onboarding's steps too, in the line of the profile's saves. The deal-breakers are a row each under a heading (#551): `DealBreakerRows`, which What you seek and `DealBreakersScreen` (the e-mail screen's door, `/profile/deal-breakers`) both show, each row opening `DealBreakerFieldScreen` at `/profile/deal-breakers/<field>`. That screen is the same for all: Everyone first, then the answers, as a filter names them (`filterOptionKey`, about somebody else, where the person's own are in the first person), saved on leaving through `useSaveOnLeave`. `saveDealBreaker` reads the whole set when its turn comes in the line of saves and swaps the one field, since the API takes the whole set. Its "Answer it" opens a later screen with `once`, which comes back instead of walking on.
